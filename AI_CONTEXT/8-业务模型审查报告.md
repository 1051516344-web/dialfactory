# DialFactory V1 · 业务模型审查报告

> 状态：待审核
> 范围：仅审查业务逻辑与生产管理合理性，不涉及技术实现
> 方法：以跟单员日常动线为视角，逐实体、逐字段审查

---

## 一、生产现场还原

在审查数据模型之前，必须先还原**真实的生产现场**。数据模型服务于现场，不是反过来。

### 1.1 表盘制造的物理流程

```
粗胚 → 制一 → 制二 → 制三 → 制四 → 总QC → 客户
        │      │      │      │
        └──────┴──────┴──────┴──→ 外协供应商
```

各工序的物理实态：

| 部门 | 做什么 | 物理特征 | 对数据采集的影响 |
|------|--------|----------|------------------|
| **制一** | 冲压成型、切边、打孔 | 机械加工，单件或小批量。产出的是"粗胚半成品" | 速度快，跟单员很少在制一停留 |
| **制二** | 打磨、喷砂、纹理（CD纹/太阳纹） | 表面处理。分为机械纹理和喷砂两种路线。部分工序可能委外 | 这里是**纹理决策点**——决定了盘面的视觉基调 |
| **制三** | 电镀（银白/金色/玫瑰金等） | **全厂瓶颈**。挂架式批量生产，一挂几十到上百件。浴槽切换有成本和等待 | 跟单员在这里花最多时间——排队、出槽、颜色比对 |
| **制四** | 移印、装字钉、夜光、清洁 | 精细活，多为手工或半自动。品质问题在这里集中暴露 | 异常事件最多的地方——但不是问题的源头 |
| **总QC** | 外观检查、颜色比对、尺寸测量 | 最后关卡。每件都要看。通过率直接影响客户交期 | **唯一必须记录数量的节点** |

### 1.2 核心角色：跟单员的一天

跟单员是系统的**唯一日常操作者**。理解他的工作方式比理解数据关系更重要。

```
08:30  打开平板，看「卡住的订单」——哪个在制三停了3天？
09:00  走到制二，确认昨天打磨的订单是否完成，点"完成"
09:15  走到制三，看电镀槽今天排什么颜色。银白的订单可以合并出槽
10:00  接到通知——制四发现一批电镀色差。到制四，记录异常：色差/50件/返回电镀
11:00  打电话给外协供应商："上周发的500件喷砂什么时候回来？"
14:00  外协回来一批，到总QC验收：450件合格，30件报废，20件返回重修
15:30  制二→制三的移交：确认数量，记录交方收方
16:00  新订单录入：客户A，500件，太阳纹+银白电镀
17:00  回顾今天哪些订单推进了，哪些还在卡
```

**关键洞察：**
- 跟单员**不是每道工序都填数量**——他只在创建、移交、QC、异常时关心数量
- 跟单员**不记录时间**——他点按钮的时间就是操作时间
- 跟单员**在走动中操作**——平板单手拿，另一只手点。不能要求双手打字
- 跟单员的**核心焦虑**：什么东西卡住了？什么东西出问题了？什么东西快到期了？

### 1.3 各角色的系统参与度

| 角色 | 系统操作频率 | 主要操作 | 操作环境 |
|------|-------------|----------|----------|
| 跟单员 | **每天 20-40 次** | 推进节点、记录异常、创建订单、移交确认 | 走动中，平板单手 |
| 部门负责人 | **每天 3-5 次** | 移交确认（收方签字）、查看本部门待办 | 车间内，站立 |
| QC | **每天 5-10 次** | 记录异常、确认最终通过 | 检验台，可双手 |
| 管理层 | **每周 2-3 次** | 看统计、看延误 | 办公室，桌面电脑 |
| 车间工人 | **0 次** | 不操作系统 | — |

**推论：** 系统的交互设计应该围绕跟单员优化。管理层需要的统计是副产品，不是主产品。

## 二、业务实体审查

逐实体审查其是否对应生产现场的真实概念。

### 2.1 订单（Order）

**对应现场概念：** 客户的一张采购单。工厂接到订单后，采购粗胚、排入生产。

**审查结论：符合。** 但存在以下问题：

#### 问题 1：`base_texture` 和 `sand_type` 放在订单级是否合适？

当前设计中，这两个字段在 `orders` 表上。但生产现场的实际是：
- 同一订单的不同数量可能走不同的纹理路线（部分 CD 纹、部分太阳纹）
- 喷砂类型有时是工序执行时才确定的（看粗胚状态决定用什么砂）

**建议：**
- 如果工厂实践中**同一订单只有一种纹理和一种喷砂**，则放在订单级没问题
- 如果有分批走不同工艺的情况，这两个字段应下沉到 **节点级配置**（route_step 的快照参数），而非订单级
- **需向工厂确认**

#### 问题 2：缺少 `交期（due_date）`

跟单员每天第一件事是看"哪些订单快到期了"。当前订单表没有交期字段。

- 缺少交期，"订单是否延误"无法自动判断
- 统计分析中的"周期"需要一个参照基准
- 这是**必加字段**

#### 问题 3：`order_qty` 的计算逻辑不明确

文档说 `order_qty = rough_qty × (1 + 损耗系数)`。但：
- 损耗系数是统一的还是按客户/工艺变动的？
- 如果每道工序都有损耗，overall 损耗系数是谁定义的？

**建议：** `order_qty` 允许手动覆盖。大多数情况下跟单员直接输入订单数量，不管粗胚多少。粗胚数量是采购关心的，跟单员只关心"客户要多少"。

### 2.2 工序节点（OrderNode）

**对应现场概念：** 订单在某个工序环节的状态。是系统的核心追踪单元。

**审查结论：基本符合。** 但存在重大设计问题：

#### 问题 4（严重）：`qty_in` / `qty_out` 的期望不切实际

当前设计暗示每个节点都可以填写投入/产出数量。但生产现场的真实情况：

| 场景 | 工人是否计数 | 跟单员是否知道 |
|------|-------------|---------------|
| 制一冲压 | 只计废品数 | 不知道具体进/出 |
| 制二打磨 | 不计 | 不知道 |
| 制三电镀 | 以挂架为单位（一挂几十件） | 大概知道挂了几挂 |
| 制四移印 | 一件一件做，但不计数 | 不知道 |
| 总QC | **逐件检查，计数** | **精确知道** |
| 部门移交 | **交接时点数量** | **确认过的** |

**核心结论：除了总QC和移交时点，跟单员没有可靠的节点级数量数据。要求填写必然导致编造数据。**

**建议：V1 仅保留以下数量采集点：**
1. 订单创建时：客户要多少（`order_qty`）
2. 移交时：交了多少（`handoffs.qty`）
3. 总QC完成时：合格多少（`order_nodes.qty_out`，仅限QC类型节点）
4. 异常记录时：坏了多少（`exception_events.qty`）
5. 删除所有中间节点的 `qty_in`/`qty_out` 字段，或明确标记为"可选且不参与任何自动计算"

#### 问题 5：`rework_pass` 的返工行为不完整

`rework_pass` 记录"这是第几次返工"，但没有回答：
- 返工后，这个新节点的前驱节点是什么？（原来的节点还是原来的前驱节点？）
- 返工节点的后续节点是什么？（继续原路线还是跳到特定节点？）

**建议：** 不影响 V1 的简化做法——返工时创建一个新的 order_node：
- `process_id` = 目标工序
- `rework_pass` = 原节点.rework_pass + 1
- `seq` 需要重新计算：插入到路线中的正确位置
- 原节点保持 `status = done`（已完成过一次，记录保留）

V1 的返工只支持"回到当前工序重做"和"回到制一重来"。复杂的返工路由留给 V2。

#### 问题 6：五态模型中的 `handing_off` 是否必要？

从生产现场看，移交有两种情况：

**情况A：同厂区内部门间移交**
- 制二把做好的盘面送到制三
- 物理上就是从一个车间推到另一个车间
- 往往没有正式的"验收"动作——收方默认接收，有问题再退
- 这种情况下，`active → handing_off → done` 三步太繁琐

**情况B：外协发出/返回**
- 寄到外部供应商
- 时间跨度长（几天到几周）
- 确实有一个"发出在途"的状态
- `handing_off` 在这里有意义

**建议：** V1 保留 `handing_off` 状态但简化操作——跟单员点一次按钮完成整个移交（上游 done + 下游 active + 创建 handoffs 记录）。不让跟单员分两步操作。

### 2.3 异常事件（ExceptionEvent）

**对应现场概念：** QC或工人在某道工序发现的质量问题。

**审查结论：符合。设计合理。**

#### 问题 7：`severity` 分级缺乏可操作的判定标准

当前：致命/严重/轻微。但谁来判断？用什么标准？

在表盘制造中：
- **致命**：客户一定会退货的问题（颜色完全不对、尺寸超差、Logo 印反）
- **严重**：客户可能会投诉的问题（轻微色差、微小划痕、字钉偏位）
- **轻微**：客户不会注意到但工厂自己知道的问题（微小灰尘点、可擦除的污渍）

**建议：** 在系统中内置判定指引——当跟单员选择异常类型时，系统建议默认严重度。例如：
- 色差 → 默认"严重"
- Logo问题 → 默认"致命"
- 微小划伤 → 默认"轻微"

跟单员可以改，但默认值减少思考负担。

#### 问题 8：缺少异常发现位置 vs 异常根因位置的区分

一个常见场景：在制四发现电镀色差。异常记录在制四节点上——这是对的（在哪发现就记在哪）。但根因在制三。当前模型没有"归因工序"字段。

**建议：** V1 不处理。这是 V2 的根因分析功能。V1 只记录"在哪发现、什么问题、多少件、怎么处理"。根因追溯靠人来判断，不靠系统。

### 2.4 部门移交（Handoff）

**对应现场概念：** 两个部门之间的正式交接。

**审查结论：部分符合。过于正式化，不完全匹配现场实际。**

#### 问题 9（重要）：不是每次跨部门流转都有正式移交

生产过程存在"自然流转"——制二做好了，跟单员推进状态，制三自动变为 active。没有数量清点、没有质量门禁、没有交方收方签字。

正式移交通常只发生在：
1. 部门之间有质量争议时（制三说制二来的盘面有划痕）
2. 外协发出/返回时
3. 最终交付给客户时

**建议：V1 中 handoffs 不是节点推进的必经步骤，而是可选动作：**
- 节点推进：`active → done`（自动触发下游节点 `waiting → active`）——这是日常流转
- 正式移交：跟单员主动创建 handoffs 记录，关联两个节点——这是正式交接
- 大部分日常流转不需要 handoffs 记录

这样 `handing_off` 状态也简化了——只在"外协发出"这种场景才进入 `handing_off`（等待外部返回），内部部门间的移交直接 `done → 下游active`。

---

### 2.5 工艺（Process）和路线（Route）

**对应现场概念：** 工艺目录 = 工厂能做哪些工序。路线 = 某类订单的标准工序组合。

**审查结论：设计合理，但 V1 不需要这么复杂。**

#### 问题 10：processes 表的 13 个字段中，V1 实际需要几个？

| 字段 | V1 是否需要 | 原因 |
|------|------------|------|
| code (P01) | ✅ 需要 | 工序编号，全厂通用标识 |
| name | ✅ 需要 | 显示名称 |
| type (加工/辅助/检验/标记) | ✅ 需要 | 决定节点行为（检验类节点 qty_out 必填） |
| default_dept_id | ✅ 需要 | 节点创建时默认归属部门 |
| is_required | ✅ 需要 | 路线是否必须包含此工序 |
| need_first_piece | ⚠️ 可简化 | V1 作为节点上的一个 checkbox，不需要独立概念 |
| queue_character | ❌ 延期 | V2 的排产/瓶颈分析功能才需要 |
| quality_level | ⚠️ 可简化 | V1 可以不区分，异常记录的严重度已经表达了质量信息 |
| rework_strategy | ❌ 延期 | V1 返工人工判断，不需要系统自动路由 |
| rework_target_id | ❌ 延期 | 同上 |
| is_active | ✅ 需要 | 软删除/停用 |
| version | ⚠️ 可简化 | V1 路线少，手动管理版本即可 |

**建议：V1 的 processes 表缩减为 7 个核心字段：code, name, type, default_dept_id, is_required, is_active, note。**

#### 问题 11：`route_snapshot` 的定位合理

订单创建时把路线步骤展开为节点，这是正确的设计。路线模板和订单实例解耦。确认保留。

### 2.6 缺失的实体

#### 缺失 1：交期追踪（Due Date）

订单表缺少 `due_date`。这是跟单员的首要工作依据。

**建议：** `orders` 表增加 `due_date DATE`。V1 首页的订单列表默认按"是否临近交期"排序。

#### 缺失 2：客户沟通记录

跟单员经常需要记录"我跟客户说了什么"。例如："客户同意延期3天""客户要求改电镀颜色"。

这不需要复杂的 CRM。一个简单的备注就够了。但当前 `orders.note` 只有一段自由文本，不够——因为跟单员可能在不同时间追加多条沟通记录。

**建议：** V1 暂不加表，但 `orders.note` 的设计应支持追加式（每条备注带时间戳），而非覆盖式。可以用 `note` 字段存储 JSON 数组 `[{time, text}]`，或新增 `order_notes` 表（V2）。

#### 缺失 3：外协发出/返回的追踪单元

当前设计把外协作为 `order_nodes` 的一个标记（`is_outsourced + supplier_id`），但没有回答：
- 发出日期
- 预计返回日期
- 实际返回日期
- 发出数量 vs 返回数量 vs 验收数量

这些字段当前分散在节点的时间字段中，但语义不匹配——外协发出是一个独立事件，不是节点的时间属性。

**建议：** V1 为外协节点增加专用字段（或复用节点的 `started_at`/`ended_at` 但语义明确为"发出日"/"返回日"）。数量对比（发出 vs 返回 vs 验收）通过 `qty_in`/`qty_out` 和外协供应商侧的对比来实现，但 V1 可以只记录不自动对比。

## 三、数据采集必要性分析

不是所有"能填"的数据都"该填"。以下按字段逐一判定必要性。

### 3.1 必须采集（不采集系统无法运转）

| 字段 | 位置 | 采集时机 | 采集方式 |
|------|------|----------|----------|
| 订单号 | orders.order_no | 创建订单 | 手动输入 |
| 客户 | orders.customer_id | 创建订单 | 下拉选择 |
| 订单数量 | orders.order_qty | 创建订单 | 数字输入 |
| 交期 | orders.due_date | 创建订单 | 日期选择 |
| 工艺路线 | orders.route_id | 创建订单 | 模板选择 |
| 节点状态 | order_nodes.status | 推进节点 | 按钮点击 |
| 异常类型 | exception_events.type | 记录异常 | 列表选择 |
| 异常数量 | exception_events.qty | 记录异常 | 数字输入 |

**共计 8 个必填字段。** 不填则系统无法回答核心问题。

### 3.2 强烈建议采集（不采集影响统计但系统可运转）

| 字段 | 位置 | 价值 |
|------|------|------|
| QC 节点产出数量 | order_nodes.qty_out (type=检验) | 最终良率统计的唯一数据源 |
| 移交数量 | handoffs.qty | 部门间数量差异追溯 |
| 异常处理方式 | exception_events.resolution | 统计"返工率 vs 报废率" |
| 订单创建时间 | orders.created_at | 自动记录 |
| 节点状态变更时间 | order_nodes.updated_at | 自动记录（非用户填写） |

**共计 5 个建议字段。** 不填系统可运转，但统计分析会缺数据。

### 3.3 可选采集（有更好、没有不影响）

| 字段 | 位置 | 备注 |
|------|------|------|
| 底质处理 | orders.base_texture | 如已体现在路线选择中则可省略 |
| 电镀颜色 | orders.plate_color | 同上——路线可能已隐含颜色 |
| 喷砂类型 | orders.sand_type | 同上 |
| 节点开始/结束时间 | order_nodes.started_at/ended_at | 跟单员手动填日期。自动记录的 updated_at 已能推算耗时 |
| 节点投入/产出数量（非QC） | order_nodes.qty_in/qty_out | 不填不影响流转 |
| 备注 | order_nodes.note | 自由文本 |
| 异常严重度 | exception_events.severity | 不选则默认"严重" |
| 异常详细描述 | exception_events.detail | 类型+数量通常已够 |

### 3.4 不建议在 V1 采集

| 字段 | 原因 |
|------|------|
| 粗胚数量 | 跟单员不关心粗胚。这是采购的事。如果不需要，删除 `rough_qty` |
| 首件确认结果 | V1 没有足够人力做首件。保留 `need_first_piece` 标记但不用独立表 |
| 审计日志 | 自动记录 created_at/updated_at 已经提供了基本追溯。完整事件溯源 V2 |
| 排队特性 (queue_character) | 数据分析需求，不是操作需求 |

## 四、现场录入负担评估

以"跟单员单手操作平板"为标准，评估每个操作的负担等级。

### 负担等级定义

| 等级 | 操作 | 举例 | 容忍度 |
|------|------|------|--------|
| 🟢 低 | 点一次按钮 | 推进节点、切换状态 | 可高频使用 |
| 🟡 中 | 选一个选项 + 点确认 | 选择异常类型、选择客户 | 每天可做 20 次 |
| 🟠 中高 | 选一个选项 + 填一个数字 + 点确认 | 记录异常（类型+数量） | 每天可做 10 次 |
| 🔴 高 | 填写多个字段 | 创建新订单 | 每天可做 5 次 |
| ⛔ 不可接受 | 输入长文本、精确时间 | 备注长文、手动输入时分 | 工厂现场几乎不会发生 |

### 逐操作评估

| 操作 | 必填字段数 | 选填字段数 | 文本输入 | 负担 | 建议 |
|------|-----------|-----------|---------|------|------|
| 推进节点（active→done） | 0 | 2（时间、数量） | 0 | 🟢 | 点一下就走。最优体验 |
| 推进节点（done→handing_off） | 1（移交数量） | 2（交方收方） | 0 | 🟡 | 数量必填是合理的 |
| 记录异常 | 2（类型、数量） | 3（严重度、处理、描述） | 1（描述） | 🟡 | 类型用图标+文字按钮，不用下拉 |
| 创建订单 | 4（号、客户、数量、路线） | 4（交期、纹理、颜色、喷砂） | 1（订单号） | 🔴 | 考虑模板化：选了客户自动推荐路线 |
| 移交确认 | 1（确认通过/拒收） | 1（收方签名） | 0 | 🟢 | 本质上是一个按钮 |
| 外协追踪 | 3（供应商、发出数量、发出日） | 1（预计返回日） | 0 | 🟡 | 可接受 |

### 负担消减策略

1. **推进节点 = 全屏大按钮。** 跟单员走到制二，看到做完了，拿出平板，点一个绿色的"完成"按钮。不需要确认弹窗。如果点错了，撤销即可。

2. **异常类型用图标代替文字。** 色差 = 🎨 图标，划伤 = 🔪 图标，沙眼 = 🕳️ 图标。比下拉列表快得多。

3. **"智能默认值"减少选择。** 推进节点时，系统预判：上一个节点在制二 active → 这个节点推进后，建议下一个节点在制三激活。不需要跟单员选择"下一个是什么"。

4. **创建订单模板化。** 选客户 → 自动推荐常用路线和电镀颜色。90% 的订单是重复的。

## 五、V1 功能优先级判定

### 5.1 判定原则

| 原则 | 说明 |
|------|------|
| P1：回答核心问题 | 能让跟单员回答"订单在哪？卡了多久？有什么问题？" |
| P2：数据底线 | 能积累最基础的数据用于后续分析（QC 通过数、异常类型） |
| P3：操作效率 | 操作必须比现有流程（纸质/口头）快 |
| P4：延后原则 | 不是 P1/P2/P3 的功能一律延后，不管多想要 |

### 5.2 功能分级

#### ✅ V1 必须（不做的后果：系统没用）

| 功能 | 覆盖 P 原则 | 说明 |
|------|------------|------|
| **订单创建** | P1 | 填 4 个必填字段：号、客户、数量、路线 |
| **订单列表** | P1 | 默认按"卡顿时间"排序，支持按状态/部门/客户筛选 |
| **流程可视化** | P1 | 纵向线性卡片，一眼看到订单在哪道工序 |
| **节点推进** | P1 + P3 | 一键推进：active→done。自动触发下游 active |
| **异常记录** | P1 + P2 | 选择类型 + 输入数量。这是质量数据的唯一入口 |
| **状态回退** | P1 | 撤销上一次推进。基于 updated_at 的简单回滚 |

**V1 最小闭环 = 6 个功能。** 这 6 个功能实现了"跟单员日常 90% 的操作"，取代纸质跟单。

#### ⚠️ V1 应该有（不做系统能用但不完整）

| 功能 | 说明 | 如果砍掉的影响 |
|------|------|---------------|
| **移交记录** | 部门间正式交接（数量确认+质量门禁） | 流转可以继续但丢了交接数据 |
| **返工标记** | 标记节点为返工，创建返工节点 | 返工可以口头处理但无法统计 |
| **订单暂停/恢复** | 暂停整张订单（客户要求暂停、等料） | 暂停的订单会和正常订单混在一起 |
| **交期预警** | 订单接近或超过交期时红色标记 | 跟单员需要手动检查每张订单 |
| **简单统计** | 每个部门有多少 active/waiting 订单 | 管理层看不到工厂负载 |

#### ❌ V1 明确不做（延后到 V2+）

| 功能 | 延期原因 | 建议版本 |
|------|----------|----------|
| **完整外协模块** | 外协可以先用"节点+备注"模拟。独立模块需要供应商管理、发出/返回/验收闭环 | V2 |
| **首件确认流程** | 需要定义首件标准、审批流、不合格处理 | V2 |
| **统计分析看板** | 需要足够数据积累。V1 先积累数据 | V3 |
| **离线模式** | 复杂度高（同步冲突、队列管理）。V1 假设在线使用 | V2 |
| **多用户+权限** | V1 只有 1-2 个跟单员用同一账号 | V2 |
| **自动返工路由** | 返工规则需要数据验证。V1 手动处理 | V3 |
| **审计日志完整版** | created_at/updated_at 已提供基本追溯 | V2 |
| **数据导出** | V1 数据量小，Supabase 后台直接导出 | V2 |
| **工艺版本管理** | V1 路线少，手动管理 | V3 |
| **客户/供应商管理 CRUD** | V1 直接数据库插入几条记录 | V2 |

## 六、V1 建议调整方案

基于以上分析，对当前架构设计文档（7-架构设计-v1.md）提出以下调整。

### 调整 1：订单表简化

**当前（7 个业务字段）：**
```
order_no, customer_id, rough_qty, order_qty, base_texture, plate_color, sand_type, route_id
```

**建议 V1（5 个业务字段）：**
```
order_no, customer_id, order_qty, due_date, route_id
```

**变更说明：**
- `rough_qty` → 删除。跟单员不关心粗胚数
- `base_texture, plate_color, sand_type` → 合并为 `specs JSONB`。理由是：不同路线有不同的规格需求。有些路线不需要喷砂，有些路线电镀颜色是关键规格。用一个柔性字段容纳不同路线的不同规格，比三个定死字段更匹配生产实际
- `due_date` → 新增。跟单员的核心工作依据

### 调整 2：节点表简化

**当前（15 个业务字段）：**
```
process_id, process_name, process_code, dept_id, dept_name, status, seq, rework_pass,
is_outsourced, supplier_id, qty_in, qty_out, started_at, ended_at, note
```

**建议 V1（12 个字段）：**
```
process_id, process_name, dept_id, dept_name, status, seq, rework_pass,
is_outsourced, supplier_id, qty_in, qty_out, note
```

**变更说明：**
- `process_code` → 删除。显示时关联 processes 表即可
- `started_at, ended_at` → 删除作为用户填写字段。改用 `updated_at`（系统自动记录状态变更时间）来推算节点耗时。V1 不要求用户手动填写时间
- `qty_in, qty_out` → 保留但**仅 QC 类型节点（processes.type='检验'）强制要求 qty_out**。其他节点可为空，不影响流转
- `note` → 保留但明确为"选填，不影响任何逻辑"

### 调整 3：移交不再耦合节点推进

**当前设计：** 节点 `active → handing_off` → 创建 handoffs → 下游接收 → 上游 done

**建议 V1 设计：**
- 日常流转：节点 `active → done`，系统自动将下游节点 `waiting → active`。**不创建 handoffs**
- 正式移交：跟单员主动创建 handoffs，指定上下游节点。此时两个节点的状态不受影响（仅作为交接记录）
- 外协发出：节点 `active → handing_off`（等待外部），外协返回时 `handing_off → done`

这样：
- 90% 的流转不需要移交记录（减轻负担）
- 10% 的重要交接（争议、外协）有正式记录
- `handing_off` 状态仅用于外协场景

### 调整 4：异常事件增加默认值

| 字段 | V1 行为 |
|------|---------|
| type | 必填，图标按钮选择（预设 7-8 种常见缺陷） |
| qty | 必填，数字键盘 |
| severity | 选填，默认"严重"。按类型自动建议 |
| resolution | 选填，默认"待处理" |
| detail | 选填，但有预设模板（"发现于[工序名]，[数量]件出现[异常类型]"） |

### 调整 5：processes 表缩减

当前 13 字段 → V1 缩减为 **7 字段**：

```
code, name, type, default_dept_id, is_required, is_active, note
```

延后到 V2+：need_first_piece, queue_character, quality_level, rework_strategy, rework_target_id, version

## 八、待向工厂确认的问题

以下问题影响业务模型设计，需要向工厂实际运营者确认：

| # | 问题 | 为什么重要 | 建议答案 |
|---|------|----------|----------|
| Q1 | 同一订单是否会出现分批走不同工艺的情况？（如500件中300件CD纹、200件太阳纹） | 决定 base_texture/sand_type 放订单级还是节点级 | 如果会，这些字段应该下沉到节点 |
| Q2 | 跟单员日常能否获取每道工序的投入/产出数量？ | 决定 qty_in/qty_out 是否保留 | 如果只有 QC 能提供数量，就只保留 QC 的 |
| Q3 | 部门间移交是否每批都有正式交接（点数量、签字）？ | 决定 handoffs 是必经流程还是可选动作 | 如果不是，移交简化为可选记录 |
| Q4 | 跟单员是否在平板现场录入，还是回到办公室再录入？ | 决定交互设计方向 | 如果是回办公室录，可以支持更多字段 |
| Q5 | 电镀颜色、喷砂类型、底质处理——这三个信息是订单创建时就知道的，还是生产过程中决定的？ | 决定字段放在 orders 还是 node 配置 | 创建时就知道 → orders；过程中决定 → node |
| Q6 | 工厂是否区分"白班/夜班"？ | 决定时间精度 | 区分 → 需要班次字段；不区分 → 日期级足够 |
| Q7 | 外协供应商目前怎么追踪？是打电话问还是供应商主动汇报？ | 决定外协模块的紧急度 | 打电话问 → 需要系统化管理；供应商主动报 → 不紧急 |
| Q8 | 返工最常发生在哪些工序？返工通常回到哪道工序？ | 决定 rework_strategy 的优先级 | 电镀返工最常见 → 优先支持回制三 |

## 九、总结

### 架构文档中需要修正的核心问题

| # | 问题 | 严重程度 | 修正方向 |
|---|------|----------|----------|
| 1 | 每个节点都要求 qty_in/qty_out 不切实际 | 🔴 严重 | 仅 QC 节点必填 qty_out，其余可选 |
| 2 | 移交与节点推进强制耦合 | 🟠 中等 | 日常流转不需要 handoffs，移交为可选动作 |
| 3 | processes 表过度设计（13字段） | 🟠 中等 | V1 缩减为 7 个核心字段 |
| 4 | 缺少 due_date | 🔴 严重 | orders 表增加交期字段 |
| 5 | started_at/ended_at 要求用户手动输入日期 | 🟡 轻微 | V1 用系统自动记录的 updated_at 替代 |
| 6 | base_texture/plate_color/sand_type 语义不明 | 🟡 轻微 | 合并为柔性 specs 字段，或向工厂确认 |
| 7 | handing_off 状态在内部流转中过于繁琐 | 🟡 轻微 | 保留但仅用于外协场景 |

### V1 应该是什么

> **V1 是一个跟单员单手就能操作、走到车间任何地方都能推进订单、记录异常的轻量工具。它不是管理系统，是跟单员的数字化笔记本。**

如果用一句话定义 V1 的成功标准：
> **跟单员愿意把平板带到车间，而不是丢在办公桌上。**
