## 一、多规格订单影响

### 现状

真实数据中几乎每张订单都包含多个颜色/规格变体：

```
生产编号 45829: 黑 20700 + 蓝 13000 + 绿 16100 + 银白 12500 + 黑蓝 2100 = 64,400件
生产编号 45679: 浅蓝贝壳 40 + 白贝/金 50 + 白贝/玫 30 = 120件
```

工厂回答 Q-DD-01：**既有整批流转，也有分批流转。**

### V1 模型影响

当前 `orders` 表用 3 个固定字段描述规格（`base_texture` / `plate_color` / `sand_type`）。这个设计假设 "一张订单 = 一种颜色 + 一种纹理"。真实数据推翻了这一假设。

**如果分批流转：** 每种颜色/变体需要独立追踪工序进度。500 件中 300 件黑可能已完成电镀，200 件蓝还在打磨——必须分开看。

**如果整批流转：** 所有变体一起推进。只需在订单层面记录 "包含哪些颜色各多少件"，不拆分追踪。

工厂回答 "两种情况都有" 意味着模型需要同时支持两种模式。

| 方案 | 描述 | V1 复杂度 |
|------|------|----------|
| **A: V1 不拆分** | 整张订单作为一个追踪单元。颜色/数量差异记录在 `orders.note` 或 `specs JSONB`。分批流转时由跟单员口头管理 | 零 |
| **B: V1 增加 order_variants** | 在 orders 下增加 variants 子表，每个 variant 有自己的 qty + 规格。order_nodes 挂在 variant 上 | 高——新表 + 新 FK 关系 |
| **C: 柔性方案** | V1 默认整批追踪。如果跟单员需要分批，手动创建多张订单（共享订单号前缀 + A/B 后缀） | 低——利用现有模型 |

### 风险等级

🟠 **中等。** 核心流转可以不依赖变体拆分，但数据精度受损（无法精确统计每种颜色的良率）。

### 建议

**V1 采用方案 C（柔性方案）。** 

理由：
1. 真实数据中已有 A/B 后缀编号模式（45793A/45793B），工厂已经在手动拆分
2. V1 将 A/B 视为独立订单——各自有独立的 order_nodes，互不干扰
3. 不新增 entity，不修改 DDL
4. 如果 V1 运行后发现 30%+ 的订单需要手动拆分，V1.5 引入 variants 表

**specs JSONB（Phase 0-A.2 C4 预留字段）**恰好解决"记录有哪些变体"的需求：
```json
{"variants": [{"color": "黑", "qty": 20700}, {"color": "蓝", "qty": 13000}, ...]}
```

### 是否阻塞 V1

**不阻塞。** 利用 A/B 编号 + specs JSONB 即可覆盖 V1 需求。

## 二、DAG 流程影响

### 现状

53 张订单（11%）有上/下层分离路线 + 组装汇合。真实流程模式：

```
上层: 制二→车床→制二→球印→车床→电镀→制四    银白 303
下层: 制四                                      香槟 303
                                                    ↓
                                              组装（汇合点）
```

工厂回答 Q-DD-02：**上下层可以理解为两个独立订单，最后组装时合并。**

### V1 模型影响

当前 `order_nodes` 是单 seq 线性序列。上下层结构在 V1 中有三种承载方式：

| 方式 | 描述 | 适用度 |
|------|------|--------|
| **A: 线性展开** | 上层节点 seq 1-6，下层节点 seq 7-8，组装 seq 9。一条序列涵盖全部 | ✅ 简单，seq 语义不变 |
| **B: 独立订单** | 上层 = 订单 A，下层 = 订单 B，组装 = 订单 C。完全利用现有模型 | ✅ 最干净，工厂回答支持 |
| **C: DAG 模型** | order_nodes 增加 `depends_on` 字段，节点可以等待多个上游 | ❌ V1 过度设计 |

### 风险等级

🟡 **低。** 工厂回答已确认 "可以当作两个独立订单处理"。不需要 DAG。

### 建议

**V1 采用方案 B（独立订单）+ 方案 A（线性展开）的组合。**

- 如果上下层路线差异大 → 拆为两个独立订单（利用 A/B 后缀），组装作为一个独立订单
- 如果上下层路线相似、节点少 → 线性展开为同一订单的 seq 段落（上层 seq 1-N，下层 seq N+1-M，组装 seq M+1）
- `order_nodes.layer` 字段（Phase 0-A.2 C2 预留）标记节点属于上层/下层/NULL

**不需要 DAG。** `order_nodes.seq` 单字段 + `layer` 标记即可承载。

### 是否阻塞 V1

**不阻塞。** 现有 seq 模型可线性承载，不需要升级为 DAG。

## 三、挪用业务影响

### 现状

49 张订单（10%）涉及挪用。挪用模式已确认：

```
"不生产" + "挪用 45479"  →  整张订单从 45479 库存取货，不走任何工序
自产 X 件 + "挪用 XXXXX"  →  部分自产 + 部分从库存取
```

工厂回答 Q-DD-04：**被挪用的订单已在库存状态，不是两个进行中订单互相挪用。**

这个回答非常关键——它确认了挪用是**单向的库存取用**，不产生跨订单的流转依赖。

### V1 模型影响

挪用的业务语义：

```
订单 45911 数量 505 → 自产 505 件（走工序） + 从 45825 库存挪用了部分（不经过工序）
```

| 维度 | 说明 |
|------|------|
| 是否影响工序流转 | **否。** 被挪用产品已经在库存中（已完成所有工序）。不需要重新走工序 |
| 是否影响数量统计 | **是。** 如果不标记挪用，QC 产出会被错误归因 |
| 是否影响订单状态 | **否。** 挪用不影响被挪用订单（已在库存/完成状态） |
| 是否为跨订单依赖 | **否。** 是单向取用，不是双向依赖 |

### 风险等级

🟡 **低。** 挪用本质是 "产出来源标记"，不是流转控制。

### 建议

**V1 阶段用 `note` 记录挪用来源，不建模。**

理由：
1. 挪用不产生工序流转依赖——被挪用产品不需要走节点
2. 挪用的统计影响（良率虚高）在 V1 阶段可接受——V1 不做 BI
3. 跟单员已经口头管理挪用的全部信息（Excel 中的 "挪用 XXXXX" 就是证据——一行文本搞定）

V1 做法：
- 跟单员在订单 `note` 中写 "挪用 #45479 库存 XX 件"
- 如果需要区分自产 vs 挪用数量，在 `order_nodes.qty_out` 的 `note` 中注明

如果 V1 运行 3 个月后挪用频率 > 20%，V1.5 在 `order_nodes` 加 `qty_reused` + `reuse_source_order_no` 两个字段。

### 是否阻塞 V1

**不阻塞。** `note` 字段已充分承载。

## 四、组件追踪影响

### 现状

Sheet 2（"8月胶.铜圈必完单"，54,578 行）是组件级别的追踪：
- 生产编号 `NNNNNH`（H 后缀 = 组件专项订单）
- 独立流程："二外印四 点四 半消光黑 900  铜圈 点夜光"
- 有交期要求（"必完"= 必须完成）
- 有关联主订单（去掉 H 后缀对应 Sheet 1 的订单号）

### V1 模型影响

胶圈/铜圈追踪在 V1 的三种处理方式：

| 方式 | 描述 | 复杂度 |
|------|------|--------|
| **A: V1 不作为独立实体** | 胶圈信息记录在主订单的 `note` 或 `specs` 中 | 零 |
| **B: V1 把 H 订单当作普通订单** | 胶圈订单 = 一张 order，process_id 引用胶圈相关工序 | 低——利用现有模型 |
| **C: V1 新增 materials 表** | 独立物料实体，追踪采购/验收/使用 | 高 |

### 风险等级

🟡 **低。** 胶圈/铜圈不影响订单的核心工序流转。

### 建议

**V1 采用方案 B（H 订单 = 普通订单）。**

理由：
1. H 订单有生产编号、有流程、有交期——它**就是一张订单**，只是"产品"是胶圈而非表盘
2. V1 的 `orders` + `order_nodes` 模型不需要任何修改就能承载胶圈订单
3. 跟单员在创建订单时，选择"组件类路线"（胶圈路线），生成对应的节点
4. 去掉 H 后缀的编号就是主订单号——通过 `note` 或 order_no 前缀关联

**不需要新增 materials 实体。** 胶圈和表盘在 V1 的抽象层是相同的——都是有生产编号、有工序流程、有交期的 "订单"。V1.5 再评估是否需要物料主数据表。

### 是否阻塞 V1

**不阻塞。** 复用 orders 模型即可。

## 五、QC 流程影响

### 现状

工厂回答 Q-DD-09：**QC 在每个部门都存在，是隐含的。**

这意味着：
- Sheet 3 中的 P23（QC板面）、P24（排版移交）、P25（接板移交）、P35（总QC）是正确的
- 但跟单员的流程缩写中**不写 QC 步骤**——它们是默认发生的
- 每个部门交接前都有 QC 动作，但跟单员不把它当作一个需要追踪的"节点"

### V1 模型影响

| 维度 | 说明 |
|------|------|
| `processes` 表 | ✅ 已有 P23/P24/P25/P35 QC 工序，无需新增 |
| `order_nodes` | ⚠️ 路线模板是否应包含 QC 节点？还是 QC 是隐式的？ |
| 流程可视化 | ⚠️ 如果 QC 节点不在路线中，流程图上看不到 QC 步骤 |

关键设计决策：**QC 节点是显式节点还是隐式规则？**

### 风险等级

🟡 **低。** `processes` 已覆盖 QC 工序，只是使用方式待定。

### 建议

**V1 按以下规则处理 QC 节点：**

1. **P35（总QC）→ 显式节点。** 任何路线模板的最后一步必须是总QC。跟单员必须推进总QC节点才能完成订单。
2. **P23/P24/P25（部门QC）→ 不纳入路线模板。** 它们是部门内部操作，由跟单员在需要时"动态追加"（利用 Phase 0-A.2 的动态追加机制）
3. **部门移交时的 QC → 隐式。** 跟单员推进 `active → done` 时，系统内部视为 "QC 通过"，不创建独立节点

这样既保持了跟单员的操作简洁（不需要为每个不可跳过的 QC 多点按钮），又保留了 QC 数据的入口（跟单员可在需要时手动追加 QC 节点记录质量问题）。

### 是否阻塞 V1

**不阻塞。**

| 5 | QC 流程 | 🟡 低 | **否** | 总QC 显式，部门 QC 可动态追加 |

### 6.2 结论

> **五项影响均不阻塞 V1。V1 的 8 张表结构不需要任何因真实数据而起的 DDL 变更。** Phase 0-A.2 的预留字段（`specs` / `layer` / `pause_reason`）恰好覆盖了真实数据暴露的需求。

### 6.3 V1 模型与真实数据的最终匹配度

| 实体 | 真实数据匹配度 | 说明 |
|------|-------------|------|
| `orders` | **75%** | 核心字段匹配。多规格用 specs JSONB 补充 |
| `order_nodes` | **85%** | seq 线性模型可承载上下层。动态追加覆盖返工/QC |
| `processes` | **80%** | 35 道工序覆盖。少数符号待确认（3D打印/CNC） |
| `exception_events` | **70%** | 值域需按工厂回答扩充（+磨板不良/刷纹不良/重做/重洗） |
| 其他 4 表 | **95%+** | 基本完全匹配 |

**总体匹配度：~82%。** 比 Phase 0-A 评估的 55-60% 显著提升（因为有了工序清单和现场确认回答）。

## 七、Architecture Decision Proposal 列表

以下 Proposal 基于真实数据分析 + 工厂回答生成。排序 = 优先级。

### ADP-001 · 多规格采用 A/B 编号拆分

- **触发：** 真实数据 99%+ 订单有多个颜色/规格变体。工厂确认分批整批都有。
- **决策：** V1 不引入 variants 实体。多规格订单由跟单员手动拆分为 A/B 独立订单。`orders.specs` (JSONB) 记录变体清单。
- **V1 动作：** 无需 DDL 变更。创建订单 UI 支持 "从同一模板创建 A/B 子订单"。
- **延后：** V1.5 评估是否需要 `order_variants` 表。
- **阻塞 V1：** 否

### ADP-002 · 上下层采用独立订单模式

- **触发：** 53 张订单（11%）有上/下层分离路线。工厂确认 "可以当两个独立订单"。
- **决策：** V1 不引入 DAG 模型。上下层拆分 = A/B 独立订单 或 同一订单线性展开（用 `layer` 字段标记）。组装节点作为最终汇合步骤。
- **V1 动作：** 无需 DDL 变更。`order_nodes.layer` 字段（Phase 0-A.2 C2）启用标记 `'upper'` / `'lower'` / NULL。
- **延后：** V2 评估是否需要节点间 `depends_on` 依赖关系。
- **阻塞 V1：** 否

### ADP-003 · 挪用采用 note 记录

- **触发：** 49 张订单（10%）涉及挪用。工厂确认 "被挪用订单已在库存状态"。
- **决策：** V1 不建模挪用关系。跟单员在 `orders.note` 或 `order_nodes.note` 中记录 "挪用 #XXXXX 库存 XX 件"。
- **V1 动作：** 无需 DDL 变更。
- **延后：** V1.5 评估 `qty_reused` + `reuse_source_order_no` 字段。
- **阻塞 V1：** 否

### ADP-004 · 组件（胶圈/铜圈）复用订单模型

- **触发：** Sheet 2 有 H 后缀的胶圈/铜圈独立追踪单。
- **决策：** V1 不新增 `materials` 实体。H 订单 = 普通 `orders` 行。通过订单编号前缀关联主订单。
- **V1 动作：** 无需 DDL 变更。路线模板中可包含 "胶圈路线" 类型。
- **延后：** V1.5 评估是否需要 `materials` 主数据表。
- **阻塞 V1：** 否

### ADP-005 · QC 节点分层处理

- **触发：** 工厂确认 "QC 在每个部门都存在但不显式写出"。
- **决策：** P35（总QC）= 显式节点，任何路线模板的最后一步。P23-P25（部门QC）= 不纳入路线模板，需要时动态追加。部门移交的 QC = 隐式。
- **V1 动作：** 无需 DDL 变更。路线模板约定最后一步为 P35。
- **延后：** 无。
- **阻塞 V1：** 否
