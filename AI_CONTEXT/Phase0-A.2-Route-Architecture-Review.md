# Phase 0-A.2 · Route Architecture Review

> 状态：Phase 0 交付物
> 触发：Phase0-A 方向调整通知 — 路线设计原则变更
> 方法：逐项审查现有 V1 模型对新原则的兼容性，输出最小必要调整
> 约束：不重新设计系统，不扩大 V1 Scope

---

## 零、新路线设计原则（引用）

| # | 原则 | 性质 |
|---|------|------|
| P1 | 工厂维护标准工艺路线模板（`process_routes`） | 保留现有 |
| P2 | 创建订单时，由业务人员选择并确认该订单实际需要执行的工序 | **新增——确认步骤** |
| P3 | 系统根据确认结果生成 `order_nodes` | 保留现有 |
| P4 | `order_nodes` 代表订单真实生产轨迹 | 保留现有 |
| P5 | 返工、重做、重洗等非计划工序允许动态追加节点 | **扩展——原仅 `repeat_node`** |
| P6 | AI 未来用于路线推荐、历史订单匹配，不作为最终决策者 | 远期，V1 不涉及 |

**P2 和 P5 是对当前 V1 模型的实质性变更点。**

## 一、process_routes 与 route_steps 审查

### 1.1 当前设计

```
process_routes (id, name, is_active)
    │
    └── route_steps (id, route_id →, process_id →, seq)
                                │
                                └── processes (code, name, type, default_dept_id, is_required, is_active)
```

**创建订单时的当前行为**（引自 [9-V1-Scope-Definition.md](9-V1-Scope-Definition.md) §七场景1、[10-Business-Model-V1.md](10-Business-Model-V1.md) 规则1）：

> 跟单员选择路线 → 系统将路线的每个步骤展开为一条工序执行记录 → 第一条记录自动设为"进行中"，其余为"等待中"

**关键特征：** 路线模板的全部步骤**无条件展开**。跟单员不参与工序选择。

### 1.2 新原则 P2 的要求

> 创建订单时，由业务人员选择并确认该订单实际需要执行的工序

这意味着：
- 路线模板是**建议集**，不是**强制集**
- 业务人员在创建订单时有一个**显式确认动作**：勾选/取消特定工序
- 确认后的工序才展开为 `order_nodes`

### 1.3 兼容性分析

| 维度 | 当前模型 | 新原则要求 | 是否兼容 |
|------|---------|-----------|----------|
| 路线作为模板 | ✅ `process_routes` + `route_steps` | 模板保留 | ✅ 完全兼容 |
| 工序可选性 | `processes.is_required` 定义工序级必修 | 业务人员在订单级决定 | ⚠️ 需区分两层语义 |
| 模板 vs 实例 | `route_snapshot` (JSONB) 记录展开结果 | 需记录"选中了什么 + 跳过了什么" | ⚠️ 需调整 snapshot 内容 |
| 路线表结构 | 2 表，4 字段 | 无需新字段 | ✅ 完全兼容 |

### 1.4 判定：兼容，无需改表，需调整 snapshot

**`process_routes` 和 `route_steps` 的表结构无需任何调整。**

理由：
- 路线模板的职责（"建议哪些工序"）不变
- 工序选择/确认是**订单创建时**的行为，应体现在订单实例上，而非模板定义上

**但有一个语义层需要明确：** `processes.is_required` 和"业务人员能否取消"之间的关系。

| processes.is_required | 业务人员能否取消 | 语义 |
|----------------------|-----------------|------|
| `true` | 否 | 全厂必修工序（如总QC）——任何路线、任何订单都不能跳过 |
| `false` | 是 | 路线建议但非强制——业务人员可根据实际情况取消 |

当前模型中 `is_required` 仅存在于 `processes` 表。这意味着"必修"是工序的固有属性，不随路线变化。这个语义在新原则下仍然正确：总QC 永远是必修的，CD纹加工在太阳纹路线上可被取消。

**无需引入 route_step 级别的 `is_optional` 字段。** 因为 V1 只有 3-5 条路线、15-20 道工序，业务人员逐项确认的认知负担很低。如果未来路线和工序增长，可在 `route_steps` 加 `is_suggested` 字段（V2）。

### 1.5 最小调整：`orders.route_snapshot` 内容变更

**当前 snapshot 语义**（引自 [7-架构设计-v1.md](7-架构设计-v1.md) §7.1）：

```json
// 当前：记录全部展开结果
{
  "route_name": "太阳纹+银白标准路线",
  "steps": [
    {"process_name": "冲压成型", "dept_name": "制一", "seq": 1},
    {"process_name": "太阳纹加工", "dept_name": "制二", "seq": 2}
    // ...所有 steps
  ]
}
```

**调整后 snapshot 语义**：

```json
// 调整后：记录模板全貌 + 确认结果
{
  "route_name": "太阳纹+银白标准路线",
  "confirmed_steps": [
    {"process_code": "P01", "process_name": "冲压成型", "dept_name": "制一", "seq": 1, "confirmed": true},
    {"process_code": "P03", "process_name": "太阳纹加工", "dept_name": "制二", "seq": 2, "confirmed": true},
    {"process_code": "P04", "process_name": "喷砂", "dept_name": "制二", "seq": 3, "confirmed": false}
    // confirmed=false 的步骤不生成 order_nodes，但保留在 snapshot 中供追溯
  ]
}
```

**变更说明：**
- 每个步骤增加 `confirmed` 布尔值
- `confirmed = true` → 生成 `order_nodes`
- `confirmed = false` → 不生成节点，但 snapshot 保留记录（回答"模板有什么但订单没选"）
- `processes.is_required = true` 的工序，`confirmed` 强制为 `true`，UI 不可取消

**这不是 schema 变更——`route_snapshot` 已是 JSONB 字段，内容结构调整不涉及 DDL。**

## 二、order_nodes 动态追加审查

### 2.1 当前设计

```sql
order_nodes (
    id, order_id, process_id, process_name, dept_id, dept_name,
    status, seq, rework_pass, qty_out, is_outsourced, supplier_id, note
)
```

**当前返工行为**（引自 [9-V1-Scope-Definition.md](9-V1-Scope-Definition.md) §三.2）：

> V1 只支持 `repeat_node`：同一工序重做，创建 rework_pass+1 的新节点，插入原节点之后

**V1 明确不做的返工策略**：`back_to_prev`、`back_to_first`、`fork`

### 2.2 新原则 P5 的要求

> 返工、重做、重洗等非计划工序允许动态追加节点

关键词是**"动态追加"**——不限于同工序重做，而是允许在任何位置插入任何类型的工序节点。

生产现场对应的真实场景：

| 场景 | 描述 | 当前 V1 是否支持 |
|------|------|-----------------|
| 电镀返工 | 在制四发现色差 → 追加一个制三电镀节点 | ❌ 仅支持 repeat_node（同位置重复） |
| 重洗 | 喷砂后发现表面污染 → 追加一个清洗节点 | ❌ 清洗可能不在原路线中 |
| 追加检验 | 发现某批次可疑 → 临时追加一个 QC 节点 | ❌ 不在原路线中 |
| 跳回重做 | 移印发现电镀问题 → 回到制三重镀 → 再回到制四移印 | ❌ back_to_prev |

### 2.3 兼容性分析

**表结构层面：** `order_nodes` 的字段设计**完全支持动态追加**。逐字段验证：

| 字段 | 动态追加场景下是否够用 | 说明 |
|------|----------------------|------|
| `id` (UUID) | ✅ | UUID 天然支持任意位置插入，不依赖数组索引 |
| `process_id` | ✅ | 可引用 `processes` 表中**任何**工序，不仅限于原路线 |
| `seq` | ✅ | 整数，插入新节点后重新计算后续节点的 seq 即可 |
| `rework_pass` | ⚠️ | 语义需澄清——见下方 §2.4 |
| `note` | ✅ | 自由文本，可记录追加原因（如 "制四发现色差，追加返工电镀"） |
| 其他字段 | ✅ | process_name/dept_name 快照在插入时自动填充 |

**操作层面：** V1 需要新增一个操作——"向订单追加节点"。

| 操作 | 当前 V1 | 调整后 V1 |
|------|---------|----------|
| 推进节点 (active→done) | ✅ 有 | ✅ 保留 |
| 暂停/恢复 (active↔paused) | ✅ 有 | ✅ 保留 |
| 返工 (repeat_node) | ✅ 有 | ✅ 保留为快捷操作 |
| **动态追加节点** | ❌ 无 | **🆕 新增** |

### 2.4 判定：结构兼容，需新增操作 + 澄清语义

**order_nodes 表结构无需调整。** UUID + seq 的设计从一开始就是为"可插入、可删除"而选的（这是 V13 → V1 的核心架构升级之一）。

**但需要澄清 `rework_pass` 的语义：**

当前 `rework_pass` 含义：同一 `order_id` + 同一 `process_id` 的第 N 次执行。

问题场景：
```
订单走制三电镀 (seq=3, rework_pass=0) → 制四移印 (seq=4) → 
追加制三电镀 (seq=4.5, ???) → 追加制四移印 (seq=5)
```

这里的"追加制三电镀"是新的 process 执行还是 rework_pass？

**建议语义规则（不改变字段，只定义规则）：**

| 追加场景 | rework_pass 取值 | seq 处理 |
|---------|-----------------|----------|
| 同工序重复（原 repeat_node） | 原节点.rework_pass + 1 | 插入原节点之后 |
| 追加新工序（原路线中有的工序） | 0（这是该工序在此订单的首次执行） | 插入指定位置 |
| 追加新工序（原路线中**没有**的工序） | 0 | 插入指定位置 |

**seq 重算规则：**
```
插入位置 N → 所有 seq ≥ N 的节点 seq += 1
新节点 seq = N
```

例如：在 seq=3 之后插入新节点 → 原 seq=4,5,6 变为 5,6,7。新节点 seq=4。

### 2.5 动态追加的触发源

动态追加是**人工触发的操作**——跟单员在流程图上点"追加工序"，选择工序类型，确认。不是系统自动决策的。

这符合 P6 原则（AI 不做决策）。V1 不做"自动推荐追加什么工序"。

## 三、processes 工序字典分类层审查

### 3.1 当前设计

```sql
processes (
    code, name, type,        -- type ∈ {加工, 检验, 辅助}
    default_dept_id, is_required, is_active
)
```

分类维度：
- `type`：加工 / 检验 / 辅助（3 个值）
- `default_dept_id`：归属部门（5 个值：制一~四 + 总QC）

### 3.2 新原则是否要求更细分类

P2 要求业务人员在订单创建时**选择并确认工序**。这意味着跟单员会面对一个工序列表，需要逐项判断"这个工序这次要不要"。

**当前组织方式已足够：**

| 跟单员的认知维度 | 模型支持 | 说明 |
|-----------------|---------|------|
| "这道工序是干什么的" | `name` | 如"银白电镀" |
| "这道工序在哪个部门" | `default_dept_id` → `departments.name` | 如"制三" |
| "这道工序能不能跳过" | `is_required` | true = 不可取消 |
| "这是加工还是检验" | `type` | 检验类节点要填 qty_out |

对于 15-20 道工序的 V1 规模，这 4 个维度足够跟单员做出确认判断。

### 3.3 判定：无需新增分类层

**不在 V1 增加 `stage`、`category`、`phase` 等分类字段。**

理由：
1. V1 工序数量少（≤20），平铺列表 + 部门分组即可
2. 确认工序时的排序遵循 `route_steps.seq`——这是生产顺序，比任何分类维度都直观
3. 如果未来工序增长到 50+，可引入 `stage` 字段（如：前段加工 / 表面处理 / 电镀 / 精细加工 / 检验）——但这是 V2 的事

## 四、是否需要新增实体

逐项排查新原则是否引入新概念：

| 可能的新概念 | 是否需要独立实体 | 理由 |
|-------------|-----------------|------|
| "工序确认记录" | ❌ 不需要 | `orders.route_snapshot` (JSONB) 中的 `confirmed` 字段已承载 |
| "节点追加记录" | ❌ 不需要 | 追加后创建的是新的 `order_nodes` 行，本身就是记录。追加原因写入 `note` |
| "路线推荐日志" | ❌ 不需要 | P6 明确 AI 推荐是 V2+ 功能，V1 无此需求 |
| "工序执行版本" | ❌ 不需要 | 同一 process 在订单中多次出现时，由 `seq` + `rework_pass` + `created_at` 区分 |
| "追加审批" | ❌ 不需要 | 动态追加是跟单员直接操作，V1 不做审批流 |

### 判定：V1 无需新增任何实体

现有 8 张表完整覆盖新原则的所有需求。

## 五、V1.5 / V2 延后清单

| # | 延后项 | 延后原因 | 目标版本 |
|---|--------|----------|----------|
| D1 | `route_steps.is_suggested` 字段 | V1 路线少，工序级 `is_required` 够用。路线级可选标记在路线/工序增多后才有价值 | V2 |

## 七、结论

**当前 V1 模型对新路线设计原则的兼容度：高（≥90%）。**

核心变更只有 3 项，且全部不涉及 DDL：

1. **`route_snapshot` 的 JSONB 内容约定**调整——记录 `confirmed` 标记
2. **V1 功能清单**增加一项——"动态追加节点"
3. **`rework_pass` 语义**文档化——区分"同工序重复"和"追加新工序"

这验证了一个关键假设：**UUID + 快照 的架构选择是正确的。** 路线模板 vs 订单实例的解耦、节点的可插入性——这两个设计决策恰好是支撑新原则的基础。

---

> **Phase 0-A.2 结论：当前 V1 模型支持新路线设计原则。3 项最小调整，0 项 DDL 变更，0 项新实体。可以继续 Phase 0 后续步骤。**
