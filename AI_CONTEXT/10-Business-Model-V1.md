# DialFactory Business Model V1

> 状态：待工厂确认
> 性质：业务模型，不是数据库设计，不是程序架构
> 目标：用结构化方式描述表盘工厂的真实业务，为后续一切技术决策提供依据

---

## 第一部分：业务实体建模

### 识别标准

一个概念被认定为"实体"需满足：
1. 在工厂日常运营中**真实存在**（不是软件概念）
2. 有**独立生命周期**（可以单独创建、变更、归档）
3. 需要**持久记录**（不是临时计算值）

### 逐实体详细建模

---

#### E1 · 客户 (Customer)

**为什么存在：**
工厂的所有订单都来自客户。没有客户概念，订单就失去了归属。17 个客户是工厂的核心业务上下文。

**现实业务对应：**
下单的品牌或手表厂。例如"时诺"、"飞亚达"等。每个客户有固定的简称、可能有不同的质量标准和交期要求。

**确认程度：** ✅ 已确认。数量（17家）、用途（订单归属）明确。

**V1 必须：** 是。没有客户，订单失去业务上下文。

**当前假设（需工厂确认）：**
- 假设 1：客户数量基本固定（17家），新增频率很低
- 假设 2：不同客户之间没有特殊的价格/质量协议需要系统记录
- 假设 3：客户只有名称有意义，不需要地址、联系人等 CRM 字段

**核心属性：**

| 属性 | 业务含义 | 确认程度 |
|------|---------|----------|
| 客户名称 | 品牌全称，如"深圳时诺钟表有限公司" | ✅ |
| 客户简称 | 工厂日常称呼，如"时诺" | ✅ |
| 是否活跃 | 是否仍在合作 | ⚠️ 假设 |

#### E2 · 订单 (Order)

**为什么存在：**
订单是整个生产活动的起点。工厂接到订单 → 采购粗胚 → 安排生产 → 交付。没有订单，后续一切追踪没有载体。

**现实业务对应：**
客户发来的一张采购单："500 个太阳纹银白表盘，8 月 20 日交货"。工厂接到后，转化为内部生产订单。

**确认程度：** ✅ 已确认。订单号、客户、数量、交期——这四个概念在 V13 已验证。

**V1 必须：** 是。系统的核心追踪单元。

**当前假设（需工厂确认）：**
- 假设 1：一张订单只有一种产品规格（不会出现"500个中300个CD纹、200个太阳纹"）
- 假设 2：交期是客户指定的，不是工厂推算的
- 假设 3：订单数量 = 客户要的数量，粗胚数量是采购关心的，跟单员不关心
- 假设 4：订单创建后，规格（纹理/颜色/喷砂）不会变更
- 假设 5：订单可以被"暂停"（客户要求暂停、等料等）

**核心属性：**

| 属性 | 业务含义 | 确认程度 |
|------|---------|----------|
| 订单编号 | 唯一标识。可能格式如"CUST-2026-0088" | ✅ |
| 所属客户 | 谁下的单 | ✅ |
| 订单数量 | 客户要多少件 | ✅ |
| 交期 | 什么时候要交货 | ✅ |
| 底质纹理 | 无底纹/太阳纹/CD纹——盘面的基础纹理 | ✅ |
| 电镀颜色 | 如银白60s、金色、玫瑰金 | ✅ |
| 喷砂类型 | 重砂/轻砂/中砂/无 | ✅ |
| 工艺路线 | 这批订单走哪条标准路线 | ✅ |
| 当前状态 | 生产中/暂停/完成——由工序执行记录自动推断 | ✅ |
| 备注 | 跟单员自由记录的信息 | ✅ |
| 创建时间 | 什么时候录入的 | ✅ |

#### E3 · 工序 (Process)

**为什么存在：**
工序是工厂的"能力目录"。工厂能做冲压、打磨、喷砂、电镀、移印、检验……这些是独立于订单存在的。一套工序目录 = 工厂的能力说明书。

**现实业务对应：**
每道工序对应车间里的一项实际操作。编号（P01、P02…）是工厂内部的统一语言。跟单员说"去 P05"，大家都知道是电镀。

**确认程度：** ✅ 已确认。P01-P99 编号体系、加工/辅助/检验分类已在知识库中定义。

**V1 必须：** 是。订单创建时需要选择路线，路线由工序组成。

**当前假设（需工厂确认）：**
- 假设 1：工序数量在 20-30 个以内（不是几百个）
- 假设 2：工序分为 3 类：加工（物理改变产品）、检验（检查质量）、辅助（等待/运输/外协）
- 假设 3：每个工序默认归属一个部门
- 假设 4：工序之间的顺序关系由路线定义，工序本身不知道"前后是谁"
- 假设 5：存在"必选工序"——任何路线都不能跳过（如总QC）

**核心属性：**

| 属性 | 业务含义 | 确认程度 |
|------|---------|----------|
| 工序编号 | P01-P99，工厂统一编码 | ✅ |
| 工序名称 | 如"银白电镀""CD纹加工" | ✅ |
| 工序类型 | 加工/检验/辅助 | ✅ |
| 默认执行部门 | 通常由哪个部门做 | ✅ |
| 是否必经 | 是否任何路线都不能跳过 | ⚠️ 需确认 |
| 是否活跃 | 是否仍在使用（停用的旧工序保留编号） | ⚠️ 需确认 |

---

#### E4 · 工艺路线 (Process Route)

**为什么存在：**
不是每种表盘都走完全相同的工序。太阳纹+银白的路线和 CD 纹+金色的路线不同。路线是"某类产品的标准流程"，让跟单员创建订单时不用每次手动选工序。

**现实业务对应：**
工厂经过长期实践，总结出 3-5 条常用路线。例如"标准银白路线：制一冲压→制二太阳纹→制三银白电镀→制四移印→总QC"。跟单员在创建订单时，选路线模板 → 确认/调整实际执行的工序 → 系统根据确认结果生成工序执行记录。

路线是**建议模板**，不是强制清单。跟单员可根据订单实际情况取消非必修工序（如跳过喷砂）、或在生产过程中动态追加非计划工序（如返工、重洗）。

**确认程度：** ✅ 已确认。V13 的"模板化创建订单"验证了路线概念。

**V1 必须：** 是。订单创建依赖路线。

**当前假设（需工厂确认）：**
- 假设 1：工厂常用路线数量有限（3-5 条），不是几十条
- 假设 2：路线一旦应用到订单上，后续修改路线不影响已创建的订单（快照）
- 假设 3：路线是线性序列，没有分支或条件跳转
- 假设 4：路线有一个"名称"用于选择，如"标准银白路线"
- 假设 5：路线是建议模板。跟单员创建订单时可取消非必修工序，`confirmed` 标记记录在订单快照中（Phase 0-A.2 新增）

**核心属性：**

| 属性 | 业务含义 | 确认程度 |
|------|---------|----------|
| 路线名称 | 如"标准银白路线""CD纹+金色路线" | ✅ |
| 包含的工序列表 | 按顺序排列的工序 | ✅ |
| 是否启用 | 废弃的路线可以停用 | ⚠️ 假设 |

---

#### E5 · 部门 (Department)

**为什么存在：**
工厂物理上分为不同车间。跟单员需要知道"订单现在在哪个部门"。部门也是责任归属——质量问题、交期延误需要定位到部门。

**现实业务对应：**
5 个部门（制一、制二、制三、制四、总QC），在物理上是不同的车间区域。每个部门有不同的设备、人员和职能。

**确认程度：** ✅ 已确认。5 个部门，类型（生产/检验），顺序固定。

**V1 必须：** 是。工序执行记录需要关联部门。

**当前假设（需工厂确认）：**
- 假设 1：部门数量和名称固定不变
- 假设 2：每个部门内部不再细分（如制二内部不再分"打磨组""喷砂组"）
- 假设 3："总QC"属于一个独立部门，有其自己的工序执行记录

**核心属性：**

| 属性 | 业务含义 | 确认程度 |
|------|---------|----------|
| 部门名称 | 制一/制二/制三/制四/总QC | ✅ |
| 顺序 | 1→2→3→4→QC | ✅ |
| 类型 | 生产/检验 | ✅ |

#### E6 · 工序执行记录 (Process Execution)

**为什么存在：**
这是整个系统的**核心追踪单元**。一张订单"现在在哪"、"卡了多久"、"谁在负责"——这三个问题全部由工序执行记录回答。

工序（E3）是模板，工序执行记录是实例。就像"菜谱"和"今天中午实际做的那道菜"的区别。

**现实业务对应：**
跟单员走到制二车间，看到订单 #0088 在打磨。"打磨"是工序，#0088 的打磨执行记录"正在进行中"是这道工序在这张订单上的实际状态。如果打磨返工了，就是第二条执行记录——同工序、同订单、第二次执行。

**确认程度：** ✅ 已确认。这是 V13 的"节点"概念，已验证为核心循环。

**V1 必须：** 是。没有它，订单追踪失去粒度。

**当前假设（需工厂确认）：**
- 假设 1：工序执行记录的状态只有 4 种：等待、进行中、已完成、暂停
- 假设 2：同一订单的同一工序可以有多次执行记录（返工），用"第N次"区分
- 假设 3：执行记录按顺序推进——上一个完成，下一个才能开始
- 假设 4：只有类型为"检验"的执行记录才强制要求产出数量

**核心属性：**

| 属性 | 业务含义 | 确认程度 |
|------|---------|----------|
| 所属订单 | 哪张订单 | ✅ |
| 对应工序 | 执行哪道工序（模板引用） | ✅ |
| 工序名称快照 | 记录创建时的工序名称（工序改名不影响历史） | ✅ |
| 执行部门 | 在哪个部门执行 | ✅ |
| 部门名称快照 | 记录创建时的部门名称 | ✅ |
| 当前状态 | 等待/进行中/已完成/暂停 | ✅ |
| 执行顺序 | 在订单的所有执行记录中排第几 | ✅ |
| 返工次数 | 0=正常，1=第一次返工，2=第二次返工…… | ✅ |
| 产出数量 | 仅检验类型必填——这道工序产出了多少合格品 | ✅ |
| 备注 | 跟单员自由记录 | ✅ |
| 状态变更时间 | 最后一次状态变更是什么时候（自动记录） | ✅ |

#### E7 · 质量事件 (Quality Event)

**为什么存在：**
"为什么停"是系统的核心问题之一。质量事件回答的就是这个问题。它记录了在哪个环节发现了什么问题、影响多少件、怎么处理。

**现实业务对应：**
QC 或工人在某道工序发现了缺陷。"这 30 件电镀色差，退回制三重镀"。这就是一条质量事件。

**确认程度：** ✅ 已确认。独立记录异常是 V13 验证的核心功能。

**V1 必须：** 是。回答 Q3（为什么停）的唯一数据源。

**当前假设（需工厂确认）：**
- 假设 1：质量事件总是关联到某条工序执行记录（"在哪发现"）
- 假设 2：缺陷类型可以用预设列表覆盖（色差/电镀不良/划伤/沙眼/变形/其他）
- 假设 3：处理方式可以用预设列表覆盖（返回电镀/返回磨板/重做/特采/报废）
- 假设 4：V1 不需要记录缺陷严重度（致命/严重/轻微）
- 假设 5：V1 不需要追溯缺陷根因（在哪道工序产生的）

**核心属性：**

| 属性 | 业务含义 | 确认程度 |
|------|---------|----------|
| 关联执行记录 | 在哪道工序的执行过程中发现的 | ✅ |
| 缺陷类型 | 色差/电镀不良/划伤/沙眼/变形/其他 | ✅ |
| 影响数量 | 多少件有问题 | ✅ |
| 处理方式 | 返回电镀/返回磨板/重做/特采/报废 | ✅ |
| 记录时间 | 什么时候发现的（自动记录） | ✅ |

## 第二部分：数据字典

以下字段不写 SQL。只回答：这个字段解决什么业务问题。

---

### 客户

| 字段 | 类型 | 必填 | 解决什么业务问题 |
|------|------|------|-----------------|
| 客户名称 | 文本 | 是 | 识别"谁下的单"。用于订单列表筛选、异常追溯时的客户沟通 |
| 客户简称 | 文本 | 是 | 工厂日常口语中的称呼。订单列表显示简称而非全称，节省空间 |
| 是否活跃 | 是/否 | 是 | 区分"正在合作"和"已停合作"，避免跟单员误选已停客户 |

---

### 订单

| 字段 | 类型 | 必填 | 解决什么业务问题 |
|------|------|------|-----------------|
| 订单编号 | 文本 | 是 | 全厂唯一标识。跟单员搜索、客户询问、标签打印——都依赖编号 |
| 所属客户 | 引用客户 | 是 | 回答"谁的货"。决定交期优先级（大客户优先） |
| 订单数量 | 数字 | 是 | 回答"要做多少"。创建订单时填一次，跟单员全程参照这个数字 |
| 交期 | 日期 | 是 | 回答"什么时候要"。交期预警的唯一参照。超过交期标红 |
| 底质纹理 | 选项 | 是 | 定义产品规格。决定走哪条路线（CD纹和太阳纹的工艺路线不同） |
| 电镀颜色 | 文本 | 是 | 定义产品规格。决定电镀工序的参数（银白60s/金色/玫瑰金） |
| 喷砂类型 | 选项 | 是 | 定义产品规格。决定是否需要喷砂工序 |
| 工艺路线 | 引用路线 | 是 | 回答"走什么流程"。创建订单时选路线，系统自动展开为工序执行记录 |
| 当前状态 | 自动计算 | 自动 | 回答"订单还活着吗"。从工序执行记录推导，不手动设置 |
| 备注 | 文本 | 否 | 跟单员的便签。记录客户沟通、特殊要求、异常情况 |

---

### 工序

| 字段 | 类型 | 必填 | 解决什么业务问题 |
|------|------|------|-----------------|
| 工序编号 | 文本 | 是 | 工厂统一编码（P01-P99）。跨部门沟通的标准语言 |
| 工序名称 | 文本 | 是 | 描述"做什么"。显示在流程图上 |
| 工序类型 | 选项 | 是 | 决定行为差异——检验类型的执行记录必须填报产出数量 |
| 默认执行部门 | 引用部门 | 是 | 创建执行记录时默认分配到哪个部门 |
| 是否必经 | 是/否 | 否 | 标记哪些工序任何路线都不能跳过（如总QC） |
| 是否启用 | 是/否 | 是 | 停用旧工序时保留编号和名称，历史订单仍可查看 |

---

### 工艺路线

| 字段 | 类型 | 必填 | 解决什么业务问题 |
|------|------|------|-----------------|
| 路线名称 | 文本 | 是 | 跟单员创建订单时的选择项。如"标准银白路线" |
| 是否启用 | 是/否 | 是 | 淘汰的路线停用但保留，历史订单仍可追溯 |

### 路线包含的工序（子表）

| 字段 | 类型 | 必填 | 解决什么业务问题 |
|------|------|------|-----------------|
| 所属路线 | 引用路线 | 是 | 这条工序属于哪条路线 |
| 工序 | 引用工序 | 是 | 哪道工序 |
| 顺序号 | 数字 | 是 | 在路线中排第几。决定执行顺序 |

---

### 部门

| 字段 | 类型 | 必填 | 解决什么业务问题 |
|------|------|------|-----------------|
| 部门名称 | 文本 | 是 | 制一/制二/制三/制四/总QC |
| 顺序号 | 数字 | 是 | 部门在工厂流程中的前后顺序。1→2→3→4→QC |
| 部门类型 | 选项 | 是 | 生产/检验。区分"制造部门"和"检验部门" |

---

### 工序执行记录（核心追踪单元）

| 字段 | 类型 | 必填 | 解决什么业务问题 |
|------|------|------|-----------------|
| 所属订单 | 引用订单 | 是 | 回答"这是哪张订单的工序" |
| 对应工序 | 引用工序 | 是 | 回答"执行的是哪道工序" |
| 工序名称快照 | 文本 | 自动 | 防止工序改名后历史记录不可读。创建时自动复制 |
| 执行部门 | 引用部门 | 是 | 回答"订单现在在哪个部门" |
| 部门名称快照 | 文本 | 自动 | 同上，创建时自动复制 |
| 当前状态 | 选项 | 是 | 回答"这道工序做完了没有"。4 种状态：等待/进行中/已完成/暂停 |
| 执行顺序 | 数字 | 是 | 在订单的所有执行记录中排第几。决定流程图的纵向顺序 |
| 返工次数 | 数字 | 自动 | 0=正常执行，1=第一次返工，2=第二次返工……用于流程图颜色标记（返工越多次，颜色越深）。语义规则（Phase 0-A.2 明确）：同工序重复执行时递增（repeat_node 快捷操作）；动态追加新工序时设为 0（这是该工序在此订单的首次执行） |
| 产出数量 | 数字 | 条件必填 | 仅工序类型为"检验"时必填。回答"最终合格多少件" |
| 备注 | 文本 | 否 | 跟单员的现场记录 |
| 创建时间 | 时间戳 | 自动 | 工序执行记录什么时候生成的（订单创建时） |
| 最后更新时间 | 时间戳 | 自动 | 最后一次状态变更的时间。回答"卡了多久"的核心数据 |

| 字段 | 类型 | 必填 | 解决什么业务问题 |

## 第三部分：业务关系模型

### 3.1 核心关系链

```
客户 (Customer)
  │
  │ "一个客户可以下多个订单"
  │
  ▼
订单 (Order)
  │
  ├─── "一张订单选择一条工艺路线"
  │     │
  │     ▼
  │   工艺路线 (Process Route)
  │     │
  │     │ "一条路线包含多个工序，按顺序排列"
  │     │
  │     ▼
  │   路线工序关联 (Route-Step)
  │     │
  │     │ "每个步骤引用一道工序"
  │     │
  │     ▼
  │   工序 (Process) ──── "每道工序默认归属一个部门" ──── 部门 (Department)
  │
  │
  │ "一张订单展开为多条工序执行记录"
  │
  ▼
工序执行记录 (Process Execution)
  │
  ├─── "每条执行记录引用一道工序（快照）"
  │
  ├─── "每条执行记录归属一个部门（快照）"
  │
  ├─── "同订单+同工序可以有多条执行记录（返工），用返工次数区分"
  │
  └─── "一条执行记录可以关联多个质量事件"
        │
        ▼
      质量事件 (Quality Event)
```

### 3.2 数量关系

```
客户 1 ──── N 订单
        （一个客户可以下多个订单）

订单 1 ──── 1 工艺路线
        （一张订单选择一条路线）

订单 1 ──── N 工序执行记录
        （一张订单展开为多条工序执行记录）

工艺路线 1 ──── N 路线工序关联
            （一条路线包含多个工序）

路线工序关联 N ──── 1 工序
            （每个步骤引用一道工序）

工序 N ──── 1 部门
        （每道工序默认归属一个部门）

工序执行记录 N ──── 1 工序
            （每条执行记录引用一道工序模板）

工序执行记录 N ──── 1 部门
            （每条执行记录归属一个部门）

工序执行记录 1 ──── N 质量事件
            （一条执行记录可以关联多个质量问题）

工序执行记录 1 ──── N 工序执行记录（返工）
            （同订单同工序，用返工次数字段关联）
```

### 3.3 关键业务规则

**规则 1：订单创建 = 路线模板确认 → 实例化**
> 跟单员创建订单时选择路线模板 → 系统展示路线包含的全部建议工序 → 跟单员确认/调整（`is_required=true` 的工序不可取消，其余可取消） → 系统根据确认结果将每步展开为一条工序执行记录 → 第一条记录自动设为"进行中"，其余为"等待中"。
>
> 订单快照（`route_snapshot` JSONB）记录模板全貌 + 每步的 `confirmed` 标记，供后续追溯。（Phase 0-A.2 新增确认步骤）

**规则 2：工序推进 = 状态传递**
> 跟单员将当前执行记录标记为"已完成" → 系统自动将下一条"等待中"的记录变为"进行中"。

**规则 3：返工 = 新记录 + 计数递增（快捷方式）**
> 跟单员在某条执行记录上点"返工"（repeat_node 快捷操作） → 系统创建一条新记录：同工序、返工次数=原记录+1、状态"进行中" → 新记录插入原记录之后、下一条记录之前 → seq 自动重算。原记录保持"已完成"。

**规则 3b：动态追加节点（通用方式，Phase 0-A.2 新增）**
> 跟单员在流程图上点"追加工序" → 选择工序类型（可从 `processes` 字典中任选）和插入位置 → 系统创建新节点：指定 process_id、rework_pass=0、状态"进行中" → 插入位置 N 后所有 seq ≥ N 的节点 seq += 1 → 新节点 seq = N。追加原因写入 `note`。适用于：退回前面工序重做、追加清洗/检验、任何路线模板未包含的临时工序。

**规则 4：订单状态自动计算**
> 所有执行记录 = 已完成 → 订单"完成"
> 存在非"已完成"的记录，且全部非"已完成"记录 = "暂停" → 订单"暂停"
> 其余情况 → 订单"生产中"

**规则 5：暂停不阻塞下游**
> 当一条执行记录被暂停时，下游的"等待中"记录不会被激活。恢复后继续流转。

**规则 6：检验节点的数量约束**
> 工序类型为"检验"的执行记录，标记"已完成"时必须填写产出数量。这是全流程唯一强制要求数量的节点。
