## 1. 用户是谁，怎么跟他配合

**一句话**：广州表盘厂的生产负责人，一个人维护这套系统（没有运维团队），同时在学日语，现场时间碎片化。

### 1.1 他的真实工作节奏（决定系统怎么设计）

- 每天**上午**在车间，可能去多次；下午和晚上**不在**。
- 晚上与周末有加班：一道工序可能**一晚横跨 1–3 道**，周末加班可能横跨**整个部门**。
- 因此：**工序起止时间戳不精确**，任何依赖"精确卡滞时长"的指标都不可靠。
- 他的使用方式不是盯产线，而是**巡检式**：隔一段时间去现场看一遍，看到哪算哪。

### 1.2 他的沟通与决策风格（从 520 条对话的 178 条原话归纳）

| 特征 | 具体表现 | 对 AI 的含义 |
|---|---|---|
| 先问"为什么/这是什么"，再决定做不做 | "什么叫开PR""什么叫独立工序还是既有工序的执行方式" | 先给一句人话解释，再给操作；不要一上来就堆步骤 |

## 2. 项目是什么

**DialFactory V1**：表盘厂生产追踪单页应用（SPA）。管理订单、工序流转、生产记录、异常、路线模板、分批、巡检、图纸。正在工厂试运行，实际用户 3–5 台终端（手机 + 台式机）。

### 2.1 业务模型要点（不懂这些会改错）

- **五部门**：制一 → 制二 → 制三 → 制四 → 总QC（`CONFIG.DEPT_ORDER`）。
- **工序字典** `processes`：编码 `P01…P43`，**UNIQUE，只顺延不重编号**（因为 `order_nodes.process_code` 是历史快照）。
- **节点序列**：一张订单一条路线，拆成 `order_nodes`，**同一时刻只能有一个 `active`**。
- **订单状态是派生值**：`OrderState.derive(nodes, currentStatus)`。
- **数量与损耗**：投料 = 订单数量 × (1 + 2%~5%)，**订单数量的后缀（如 `53+2%`）本身就是损耗预算**；只有**总QC（P35）**强制填产出，中间工序不强制（他看不到）。
- **巡检**：`order_inspections` 独立表，只 INSERT，**绝不写 `orders`**（会污染 `updated_at` 排序）。
- **外发/采购**：做成了具体工序（P36–P42），不是通用工序+备注。

## 4. 技术铁律（违反就会出事）

1. **零构建**：纯原生 HTML/CSS/JS，无框架、无打包器、无 npm 依赖。新增静态文件**必须**同步改 `.github/workflows/deploy.yml` 白名单（只发布 `index.html css js sw.js`）。
2. **模块模式**：IIFE 单例 `const Xxx = (() => {...})();`；页面 → `XxxAPI` → `DB.call()` → Supabase REST。`DB.call()` **不抛异常**，统一返回 `{ok, data, count}` / `{ok:false, error}`。
3. **单 active**：前端 `guardSingleActive()`（`activate`/`resume`/`undo` 共用）＋ DB 017 索引。任何改节点状态的代码都要过这道守卫。
4. **派生状态**：`OrderState.derive(nodes, currentStatus)` **必须传 currentStatus**，否则 `cancelled` 会被"复活"。
5. **巡检不写 orders**：任何写 `orders` 的操作都会刷新 `updated_at`，破坏首页与列表的"未推进时长"排序。
6. **编码不重编号**：新工序一律顺延，不改既有编码。
7. **密钥**：只在 Supabase Secrets / Cloudflare Worker 环境变量。前端只有 `anon key`（可公开）。
8. **OCR 不是直连**：Supabase(东京) → **Cloudflare Worker 代理** → 阿里云(杭州)。直连会间歇性超时（25s），这是已定架构，别"优化"回去。
9. **跨机器行尾**：那台 Windows 机器上仓库是 **CRLF 混杂**，多行锚点替换必须按文件实际 EOL。
10. **中文提交信息**：Windows/PowerShell 下必须 `git commit -F <无 BOM 的 UTF-8 文件>`，否则乱码。
11. **别信"改了没生效"**：Pages 有 10 分钟缓存，先 `Ctrl+Shift+R` 强刷；验证线上文件用 GET 不用 HEAD（PowerShell 的 HEAD 会误报 404）。

## 5. 标准工作流（这是这套系统能持续演进的原因）

### 5.1 分工

```
人（现场经验 + 决策）
  ↓ 描述现象（截图/报错/业务场景）
策略模型（网页端，强推理）：定位根因 → 给方案选项 → 写《任务书》
  ↓ 人复制任务书
DSH（执行）：只读分析 → 改代码 → 出 diff → 自测 → 不 commit 不 push
  ↓ 人复制回执（diff + 原始输出）
策略模型：审 diff → 给确认点 → 出提交/部署指令
  ↓ 人在 SQL Editor / 终端里点确认
DSH 或人：入库 → 自动部署 → 线上验收（人肉点 5 分钟）
```

### 5.2 任务书模板（这份对话里被验证了 40+ 次）

```text
在仓库 <路径>，分支 <branch>。
任务：<一句话目标>
根因（已定位）：<不写猜测，只写证据>
只做以下改动，按优先级：
【改动 1】<文件:行号> <具体做什么>
【改动 2】...
【明确不做的事】
- 不改 <文件>
- 不引入依赖
【要求】
- 每处改动加注释，注明触发场景
- 输出 unified diff，不要 commit、不要 push
- 用 <样本> 做离线验证，给出期望值对比表
```

### 5.3 回执模板

```text
1) 改了哪些文件（git status --short 原文）
2) unified diff
3) 自测结果（node --check / 桩测试 / 期望值对比）
4) 未闭环项（必须主动列出来）
```

### 5.4 为什么必须这样

- 模型会**过度发挥**（曾把"加时间徽标"改成重写整个渲染函数，导致白屏）。
- DSH 看不到浏览器，**UI 只能由人验收**；所以规则是"DSH 出 diff，人点确认"。
- 每次事故都成为了规范：锚点唯一性、导出闭环检查、行为测试，全部写进了 `HANDOFF.md §9`。
