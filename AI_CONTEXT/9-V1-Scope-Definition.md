# DialFactory V1 · Scope Definition

> 状态：待审核
> 原则：不是"能做什么"，是"不做什么"
> 目标：3 个月内可上线、可验证核心价值的生产追踪系统

---

## 一、产品目标

### 1.1 V1 只解决 5 个问题

| # | 核心问题 | V1 答案 | 不做什么 |
|---|---------|---------|----------|
| Q1 | 订单现在在哪？ | 流程图定位当前 active 节点 + 所属部门 | 不追踪人员在做什么 |
| Q2 | 卡在哪个工序？ | 任一节点停留超过 N 天自动标红 | 不自动排产、不计算产能 |
| Q3 | 为什么停？ | 异常事件挂在节点上，可查看原因 | 不自动归因、不做根因分析 |
| Q4 | 谁负责？ | 每个状态变更有操作人 + 时间戳 | 不做细粒度权限 |
| Q5 | 历史发生过什么？ | 订单完成后的完整节点轨迹可回溯 | 不做 BI、不做趋势图 |

### 1.2 V1 成功标准

> **跟单员每天的 20-40 次操作中，80% 能在 10 秒内完成。系统取代纸质跟单本。**

具体指标：
- 订单创建：≤ 60 秒（选客户、选路线、填数量、填交期）
- 节点推进：≤ 3 秒（点一个按钮）
- 异常记录：≤ 20 秒（选类型、填数量）
- 订单定位：≤ 5 秒（打开列表或流程图）

### 1.3 V1 不是

- ❌ 不是 ERP —— 不做库存、不做财务、不做排产
- ❌ 不是 MES —— 不做设备对接、不做自动化采集
- ❌ 不是 BI —— 不做数据看板、不做趋势预测
- ❌ 不是协同平台 —— 不做消息通知、不做审批流
- ❌ 不是移动 App —— 不做原生应用、不做离线模式

## 二、V1 功能范围

### 2.1 逐模块决策

| 模块 | V1 包含 | 原因 | 如果不做的后果 |
|------|---------|------|---------------|
| **订单管理** | ✅ 是 | Q1-Q5 的载体。没有订单什么都没有 | 系统无意义 |
| **工艺路线** | ✅ 是（最小） | 订单创建需要选择路线模板，然后由跟单员确认/调整具体执行的工序。V1 只支持预定义的固定路线作为模板 | 每张订单手动录入工序，不可接受 |
| **工序节点** | ✅ 是 | Q1/Q2 的核心。节点 = 追踪单元 | 系统无意义 |
| **状态流转** | ✅ 是（四态） | waiting/active/done/paused。取消 handing_off | 无法追踪进度 |
| **异常记录** | ✅ 是（最小） | Q3 的核心。type + qty + resolution | Q3 无法回答 |
| **返工** | ✅ 是（repeat + 动态追加） | 电镀返工是日常操作。V1 支持当前工序重做（repeat_node）+ 动态追加任意工序节点（重洗、退回重做等） | 返工操作会破坏流程数据 |
| **部门** | ✅ 是（只读） | Q1 需要知道"订单在哪个部门"。5 个部门预置，V1 不提供 CRUD | 无法定位订单 |
| **客户** | ✅ 是（最小） | 17 个客户预置，V1 不提供 CRUD | 订单列表无法筛选 |
| **部门移交** | ❌ 否 | 日常流转 active→done→next_active 已足够。正式移交是部门间有争议时才需要的功能 | V1 可以正常流转订单 |
| **外协** | ❌ 否 | 外协是"把货寄出去等回来"。V1 用一个标记 + 备注模拟，不做独立模块 | 外协订单可以手工标记，只是没有独立追踪 |
| **权限/多用户** | ❌ 否 | 工厂固定人员，1-2 个跟单员共用同一账号。Supabase 的 anon key + 简单密码即可 | 安全风险可接受（内网 + 受信用户） |
| **统计面板** | ❌ 否 | V1 的价值是"追踪"，不是"分析"。数据积累后再做统计 | 跟单员可以用肉眼扫订单列表判断负载 |
| **离线同步** | ❌ 否 | 见 §三.1 详细分析 | — |
| **首件确认** | ❌ 否 | 工厂可能首件是口头确认。V1 不需要信息化 | — |
| **质量门禁** | ❌ 否 | 移交本身不在 V1，门禁更不需要 | — |
| **审计日志** | ❌ 否（独立表） | created_at/updated_at 已记录每行变更时间。独立 audit_logs 表延后 | 基本追溯够用 |
| **数据导出** | ❌ 否 | V1 数据量小，Supabase 后台可查 | — |

### 2.2 V1 最终功能清单（10 项）

```
 1. 订单创建    — 选路线模板 → 确认/调整工序 → 填订单号、客户、数量、交期 → 生成节点
 2. 订单列表    — 按状态/部门/客户筛选，卡顿订单自动置顶
 3. 流程可视化  — 纵向卡片，4 种颜色状态，点击推进
 4. 节点推进    — 一键 active→done，自动触发下游 active
 5. 节点暂停    — active→paused，记录暂停原因（选异常类型）
 6. 异常记录    — 挂在节点上：类型 + 数量 + 处理方式
 7. 简单返工    — 同工序重做：rework_pass+1，新建节点（repeat_node 快捷操作）
 8. 动态追加节点 — 在任意位置插入任意工序节点（返工/重洗/退回重做），seq 自动重算
 9. 状态回退    — 撤销最近一次推进（基于 updated_at）
10. 交期预警    — 超期订单红色标记
```

> **变更说明（Phase 0-A.2）：** V1 功能从 9 项增至 10 项。新增第 8 项"动态追加节点"取代原复杂返工策略（back_to_prev/back_to_first/fork）。原第 7 项"简单返工"保留为快捷操作（repeat_node）。路线选择增加"确认/调整工序"步骤。

## 三、明确删除项

### 3.1 离线同步——删除

**原始设计：** IndexedDB + sync queue + 冲突合并 + Service Worker + PWA

**重新评估：**

| 假设 | 验证 |
|------|------|
| "工厂网络不稳定" | 是真的不穩定，还是偶尔断线？如果是偶尔断线（每天 < 30 分钟），V1 容忍"断线时不能操作"。如果是长期断线，应该先解决网络问题，再考虑离线系统 |
| "跟单员在车间走动需要离线" | 平板连 WiFi，车间内覆盖即可。如果车间无 WiFi，一个 4G 路由器（¥200）解决的问题，不要用 IndexedDB 解决 |
| "离线是核心竞争力" | V13 用 localStorage 是因为没有后端。V1 有 Supabase，离线不再是刚需 |

**离线同步的真实成本：**

| 组件 | 复杂度 |
|------|--------|
| IndexedDB schema 设计 + 迁移 | 中 |
| sync queue（操作队列、重试、顺序保证）| 高 |
| 冲突检测 + 合并策略 | 高 |
| Service Worker（缓存策略、更新管理）| 中 |
| 测试（各种断网/恢复场景）| 高 |
| 维护（bug 难以复现）| 高 |

**结论：离线同步消耗的开发时间 > 核心业务逻辑的开发时间。V1 删除。**

**替代方案：**
- 工厂部署一个 WiFi 路由器，确保车间覆盖
- 偶尔断线 → 系统显示"网络不可用，请稍后"，不需要离线写
- V1.5 评估：如果真实运营数据证明断线频率 > 容忍度，再加入离线

### 3.2 复杂返工策略——由动态追加替代

**原始设计：** 5 种 rework_strategy（none / repeat_node / back_to_prev / back_to_first / fork）

**V1 保留：** `repeat_node`（快捷操作）+ 动态追加节点（通用机制）

**原因：**

| 策略 | 现场实际频率 | V1 处理方式 |
|------|------------|------------|
| repeat_node | **高频** — 电镀色差重镀、打磨返工 | ✅ 快捷操作：新建 rework_pass+1 节点 |
| back_to_prev | 低频 — 通常口头处理 | ✅ 动态追加：跟单员手动插入目标工序节点 |
| back_to_first | 极低频 — 灾难性质量问题 | ✅ 动态追加：跟单员手动插入制一节点 |
| fork | 理论存在 — 分选合格/不合格 | ✅ 动态追加 + 备注："分选后50件继续、30件报废" |

**V1 的返工操作（两种方式）：**

**方式 A — 快捷返工（repeat_node）：**
1. 跟单员在节点上点"返工"
2. 系统创建新节点：相同 process_id、rework_pass+1、status=active
3. 原节点保持 done（已完成过一次）
4. 新节点在原节点之后、下一个节点之前插入
5. seq 自动重算

**方式 B — 动态追加（任意工序）：**
1. 跟单员在流程图上点"追加工序"
2. 选择工序类型（可从 processes 字典中任选）
3. 选择插入位置（在哪个节点之后）
4. 系统创建新节点：指定 process_id、rework_pass=0、status=active
5. seq 自动重算：插入位置 N → 所有 seq ≥ N 的节点 seq += 1
6. 跟单员在 note 中记录追加原因

**两种方式的语义区别：**

| 场景 | 使用方式 | rework_pass | 说明 |
|------|---------|-------------|------|
| 电镀色差，重镀一次 | A: 快捷返工 | 原+1 | 同工序重复执行 |
| 制四发现电镀问题，退回制三重镀 | B: 动态追加 | 0 | 追加不同工序 |
| 喷砂后表面污染，追加清洗 | B: 动态追加 | 0 | 追加路线外工序 |
| 临时追加一道检验 | B: 动态追加 | 0 | 追加辅助工序 |

**删除 back_to_* 和 fork 作为系统自动策略，改为人工决策 + 动态追加执行。** 系统不自动判断返工路由——跟单员根据现场情况决定追加什么工序。AI 推荐延后至 V1.5+。

### 3.3 复杂质量模型——删除

**原始设计：** first_piece_inspections + quality_gate (pass/reject/conditional_accept) + severity (致命/严重/轻微)

**V1 保留：** 仅 `exception_events`（type + qty + resolution）

**原因：**

| 组件 | 现场实际 | V1 处理 |
|------|---------|---------|
| first_piece_inspections | 工厂可能在做首件确认，但通常是口头+实物标记。信息化首件的价值在 V1 阶段为零——只有 1-2 个跟单员，口头沟通更快 | ❌ |
| quality_gate | 移交本身不进入 V1（见 §二），门禁更不需要 | ❌ |
| severity（致命/严重/轻微）| 分级标准未建立，选了也是拍脑袋。V1 只记录"发生了什么"，不要求判断严重度 | ❌ |
| conditional_accept（让步接收）| 高信任度场景——内部部门间不存在"拒收"文化。有问题口头沟通，不会走系统流程 | ❌ |

**V1 的异常模型（最小）：**

```
exception_events
├── type        — 色差/电镀不良/划伤/沙眼/变形/其他（预设列表）
├── qty         — 异常数量（必填）
└── resolution  — 返回电镀/返回磨板/重做/特采/报废（预设列表）
```

仅 3 个业务字段。不做 severity、不做 detail、不做 recorded_by（系统自动记录操作人）。

### 3.4 外协——删除

**原始设计：** `is_outsourced` + `supplier_id` + 外协专用时间字段 + 数量对比

**V1 决策：不进入 V1。**

**原因：**

1. **12 家外协供应商的追踪模式差异大。** 有的通过微信、有的通过电话、有的送货上门。V1 不应该在没有理解每种外协模式之前就建模。

2. **外协的核心痛点不是"记录"，是"催"。** 跟单员打电话问"什么时候回来"——这不是系统能解决的。系统只能记录"发出日"和"返回日"，但这两个日期跟单员本来就知道。

3. **外协可以在 V1 中用异常节点模拟。** 当订单需要外协时，创建一个 type='辅助' 的节点，备注写"外协喷砂-XX供应商"。发出时标记 active，返回时标记 done。不需要独立的外协表。

4. **外协的数据录入负担高。** 需要记录供应商、发出日期、发出数量、预计返回日期、实际返回日期、返回数量、验收数量——这 7 个字段在 V1 阶段没人会填。

**扩展预留：**
- `order_nodes` 表保留 `is_outsourced` 和 `supplier_id` 字段（可为 NULL）
- V1 不使用这两个字段
- V1.5 启用外协模块时，字段已在表中，无需迁移

## 四、技术架构重新选择

### 4.1 三种方案对比

| 维度 | A. 云端 SaaS（Supabase） | B. 内网服务器 | C. 混合 |
|------|--------------------------|---------------|---------|
| **服务器** | 无（Supabase 托管） | 需要一台内网机器 | 两者都要 |
| **部署** | `git push` → GitHub Pages | 需要部署流程 | 复杂 |
| **网络要求** | 需要互联网 | 仅需内网 | 两者 |
| **数据位置** | Supabase 云端 | 工厂内部 | 云端+本地 |
| **运维** | 零 | 需要维护 PG + 备份 | 最高 |
| **开发速度** | 最快 | 中等 | 最慢 |
| **离线容忍** | 需要网络 | 内网通常稳定 | 最好 |
| **成本** | Supabase 免费层 | 一台旧 PC | 两者 |
| **安全** | RLS + HTTPS | 内网隔离 | 复杂 |

### 4.2 推荐：A. 云端 SaaS

**理由：**

1. **3 个月上线目标。** 方案 B 需要采购/配置服务器、搭建网络、部署 PostgreSQL、配置备份——至少 2 周的非开发工作。方案 A 注册 Supabase 账号即用。

2. **工厂有互联网。** 平板能刷微信就能连 Supabase。如果工厂真的没有互联网，那是一个应该先解决的问题（4G 路由器 ¥200），不是架构应该妥协的问题。

3. **V13 已验证了"不需要后端服务器"的方向。** Supabase 就是这个方向的升级版——从 localStorage 升级到 PostgreSQL，而不是从零搭建服务器。

4. **安全风险可接受。** Supabase 免费层 500MB 数据库，够存几年数据。数据不涉及个人隐私、不涉及财务。RLS 配置简单（V1 只有 1-2 个用户）。

5. **如果验证失败，沉没成本最低。** 方案 A 不涉及任何硬件采购和基础设施投入。如果 3 个月后发现方向不对，损失的是开发时间，不是硬件成本。

### 4.3 V1 技术栈（最终）

| 层 | 选择 | 说明 |
|----|------|------|
| 数据库 | Supabase (PostgreSQL) | 免费层，500MB，够 V1 用 |
| API | Supabase JS Client | 前端直连，无需中间层 |
| 前端 | 纯 HTML/CSS/JS | 单文件或少量文件，不引入框架 |
| 部署 | GitHub Pages | 免费，HTTPS，自动部署 |
| 认证 | Supabase Auth（可选） | V1 可暂用 anon key + 简单密码模式 |
| 离线 | **无** | V1 在线使用 |

### 4.4 网络容错（轻量）

不做离线同步，但做**网络异常提示**：

```
if (fetch fails) {
    show "网络不可用，请检查 WiFi 连接后重试"
    // 不写入本地、不排队、不缓存
}
```

这是 5 行代码的事，不是 IndexedDB + sync queue。

### 5.1 V1 表清单

| # | 表名 | V1 包含 | 说明 |
|---|------|---------|------|
| 1 | `departments` | ✅ | 预置 5 行（制一/二/三/四/总QC），V1 无 CRUD |

| 7 | `order_nodes` | ✅ | 核心表，8 个业务字段 |
| 8 | `exception_events` | ✅ | 3 个业务字段 |

**V1 共计 8 张表。** 不是架构设计中的 15 张。

### 5.2 V1 延后表

| 表名 | 原设计位置 | 延后原因 | 目标版本 |
|------|-----------|----------|----------|
| `suppliers` | 主数据 | 外协不进入 V1 | V1.5 |
| `handoffs` | 业务表 | 移交不进入 V1，日常流转自动推进 | V1.5 |
| `first_piece_inspections` | 业务表 | 首件确认不进入 V1 | V2 |

### 5.3 V1 表结构（精简版）

```sql
-- 部门（预置数据，无 CRUD）
CREATE TABLE departments (
    id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name    TEXT NOT NULL,        -- 制一/制二/制三/制四/总QC
    seq     INTEGER NOT NULL
);

-- 客户（预置数据，无 CRUD）
CREATE TABLE customers (
    id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name    TEXT NOT NULL,
    code    TEXT                   -- 短码
);

-- 工艺目录（V1 精简：6 字段）
CREATE TABLE processes (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code            TEXT NOT NULL UNIQUE,    -- P01-P99
    name            TEXT NOT NULL,
    type            TEXT NOT NULL DEFAULT '加工',  -- 加工/检验
    default_dept_id UUID REFERENCES departments(id),
    is_required     BOOLEAN DEFAULT false,
    is_active       BOOLEAN DEFAULT true
);

-- 工艺路线
CREATE TABLE process_routes (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        TEXT NOT NULL,
    is_active   BOOLEAN DEFAULT true
);

-- 路线步骤
CREATE TABLE route_steps (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    route_id    UUID NOT NULL REFERENCES process_routes(id),
    process_id  UUID NOT NULL REFERENCES processes(id),
    seq         INTEGER NOT NULL
);

-- 订单（V1 精简：5 业务字段 + system）
CREATE TABLE orders (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_no        TEXT NOT NULL UNIQUE,
    customer_id     UUID REFERENCES customers(id),
    order_qty       INTEGER NOT NULL,           -- 订单数量
    due_date        DATE NOT NULL,              -- 交期
    route_id        UUID REFERENCES process_routes(id),
    status          TEXT DEFAULT 'in_production', -- 自动计算
    note            TEXT,
    created_at      TIMESTAMPTZ DEFAULT now(),
    updated_at      TIMESTAMPTZ DEFAULT now()
);

-- 工序节点（V1 精简：8 业务字段 + system）
CREATE TABLE order_nodes (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id        UUID NOT NULL REFERENCES orders(id),
    process_id      UUID REFERENCES processes(id),
    process_name    TEXT,                        -- 快照
    dept_id         UUID REFERENCES departments(id),
    dept_name       TEXT,                        -- 快照
    status          TEXT DEFAULT 'waiting',      -- waiting/active/done/paused
    seq             INTEGER NOT NULL,
    rework_pass     INTEGER DEFAULT 0,
    qty_out         INTEGER,                     -- 仅 type='检验' 的节点必填
    is_outsourced   BOOLEAN DEFAULT false,       -- V1 预留，不使用
    supplier_id     UUID,                        -- V1 预留，不使用
    note            TEXT,
    created_at      TIMESTAMPTZ DEFAULT now(),
    updated_at      TIMESTAMPTZ DEFAULT now()
);

-- 异常事件（V1 精简：3 业务字段 + system）
CREATE TABLE exception_events (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    node_id         UUID NOT NULL,
    type            TEXT NOT NULL,               -- 预设列表
    qty             INTEGER NOT NULL,
    resolution      TEXT,                        -- 预设列表
    created_at      TIMESTAMPTZ DEFAULT now()
);
```

## 六、V1 状态模型（简化）

### 6.1 节点四态

```
         ┌──────────┐
    ┌───►│  active  │◄───┐
    │    └────┬─────┘    │
    │         │          │
    │    ┌────┼────┐     │
    │    ▼    ▼    ▼     │
    │ ┌────┐┌──────┐┌───┐│
    │ │done││paused││...││
    │ └────┘└──┬───┘└───┘│
    │     ▲    │         │
    │     │    │ resume  │
    │     │    └─────────┘
    │     │
    │     │ (下游节点)
    │     │
    │  ┌──────┐
    └──│waiting│
       └──────┘
```

**四态替代原五态——移除 `handing_off`：**

| from | to | 触发 |
|------|-----|------|
| waiting | active | 上游节点 done（自动） |
| active | done | 跟单员点"完成" |
| active | paused | 跟单员点"暂停" + 选原因 |
| paused | active | 跟单员点"恢复" |
| active | active | 返工：创建 rework_pass+1 的新节点 |

**移除 handing_off 的原因：**
- 内部部门间流转是物理上的"推过去"，不是协议上的"交接"
- active→done 已经触发了下游的 waiting→active，跟单员只点一次按钮
- handing_off 仅在"外协发出等返回"场景有意义，而外协整体不在 V1

### 6.2 订单状态（自动计算，3 态）

| 订单状态 | 计算规则 |
|----------|----------|
| `in_production` | 存在非 done 节点，且非全部 paused |
| `paused` | 所有非 done 节点都是 paused |
| `completed` | 所有节点都是 done |

## 八、演进路线

### 路线总览

```
V1.0 ──────────── V1.5 ──────────── V2
(3个月)          (+2个月)          (+3个月)
生产透明化       部门协作          质量+供应链
```

### V1.0：生产透明化（当前）

**新增能力：**
- 订单创建 + 全流程可视化
- 四态节点追踪
- 异常记录（类型+数量+处理）
- 简单返工（同工序重做）
- 交期预警

**为什么先做这个：**
这是系统的骨架。如果没有订单能从头到尾走通，后面的一切功能都是空中楼阁。验证"数字化追踪是否比纸质更高效"是 V1 的唯一实验目的。

**前置条件：**
- 知识库：工艺节点库（04）达到 L1
- 技术：Supabase 项目创建
- 数据：至少 3 条常用路线的工艺步骤明确

**V1.0 完成标志：**
- 5 张真实订单从创建到完成全流程走通
- 跟单员每天主动使用（不是被要求使用）
- 异常数量 ≥ 10 条真实记录

---

### V1.5：部门协作

**新增能力：**
- 正式移交记录（handoffs 表启用）
- 移交时的数量确认和质量门禁
- 外协发出/返回追踪（最小模型）
- 部门待办列表（每个部门有哪些 active 节点）

**为什么这个阶段加入：**
V1.0 验证了"一个人追踪订单"可行。V1.5 验证"多部门之间用系统交接"可行。移交是部门间的正式握手——解决了"制二说交了 500 但制三说只收到 480"的问题。

**前置条件：**
- V1.0 稳定运行 ≥ 1 个月
- 至少 2 个部门之间有数量争议的真实案例（证明移交记录的必要性）
- 知识库：部门移交（06）达到 L1
- 至少 3 家外协供应商愿意配合

---

### V2：质量与供应链

**新增能力：**
- 首件确认流程
- 完整外协模块（供应商管理、发出/返回/验收闭环）
- 基础统计（不良率、返工率、平均周期）
- 数据导出（CSV）
- 审计日志（独立表）
- 多用户 + 基本权限

**为什么这个阶段加入：**
V1.5 积累了足够的移交数据和异常数据。统计不再是"看着空表画图表"，而是基于真实数据做分析。外协模块的设计也经过了 V1.5 的轻量验证。

**前置条件：**
- V1.5 稳定运行 ≥ 2 个月
- 异常记录 ≥ 100 条（统计需要样本量）
- 外协记录 ≥ 20 条（外协模式已清晰）
- 知识库：外协管理（11）达到 L1

## 十、从架构设计到 V1 的变更汇总

| 架构设计 (7-架构设计-v1.md) | V1 Scope (本文档) | 变更理由 |
|------------------------------|-------------------|----------|
| 15 张表 | **8 张表** | 移除 suppliers, handoffs, first_piece_inspections, audit_logs；合并功能 |
| 五态模型 | **四态模型** | handing_off 仅外协场景需要，外协不在 V1 |
| 离线同步 (IndexedDB + PWA) | **无离线** | 内网/4G 覆盖，断线容忍 |
| 复杂返工 (5 种策略) | **仅 repeat_node** | 低频策略人工处理 |
| 完整质量模型 | **仅 exception_events (3 字段)** | severity/first_piece/quality_gate 延后 |
| 正式移交 | **日常流转自动推进** | 移交延后至 V1.5 |
| 外协模块 | **预留字段，不启用** | 外协延后至 V1.5 |
| 审计日志独立表 | **created_at/updated_at** | 独立日志延后至 V2 |
| 统计面板 | **无** | V1 只追踪，不分析 |
