# 工作流与策略简报

> 这份文件回答一个问题：**在没有网页端额度、也不想烧钱的前提下，怎么让"策略分析"这件事不降级。**
> 结论先给：**升级来自流程和上下文，不来自换更贵的模型。** 依据是这 520 条对话里策略真正起作用的地方。

---

## 1. 现在的分工与它的天花板

```
人（现场经验 + 决策）
  → 网页端模型（深度思考 + 联网）定位根因、给方案、写任务书
  → DSH（我这台机器）执行：读代码、改文件、出 diff、跑验证
  → 人复制回执回去审查
  → 人点确认：SQL Editor / 终端 / 合并
```

**天花板在哪**：策略模型的上下文是**从零开始**的。每次都要重新解释"这个项目是什么、上次改过什么、哪些是坑"。这份对话里，光"解释背景"就占了大量轮次，真正的分析反而短。

**关键判断**：所以真正的杠杆不是"更强模型"，而是**让策略模型在开口前就知道上下文**。这也正是本套文档要解决的事。

---

## 2. 这份对话证明：策略质量来自这四样东西

不是模型档位，是这四样（每一条都能在归档里找到证据）：

| 来源 | 证据（对话中的具体例子） |
|---|---|
| **① 真实证据**（日志、样本、截图、SQL 结果） | `S01 的 prism_wordsInfo`、`Response 里的 DR951`、`ping 不通杭州` —— 有证据的定位一次就对；没证据的推测（"500 可能是权限"）基本都错了 |
| **② 范围收窄** | 每次成功的任务书都写着"只改 `extract-base-texture.js`，不要 commit"；范围一放开（"顺手把首页也改改"）就出白屏 |
| **③ 硬前提 + 明确的"不做"** | "规则必须作用在 L146–147 列筛选之前，注入 L148 无效（已实测）"——这句话省掉一整轮试错 |
| **④ 结果回灌** | 人把 diff / 报错 / SQL 结果原样贴回，策略模型才能审。DSH 的报告一旦没人回灌，就会出现"它以为改了、其实没改"（见 msg 250、msg 413） |

**推论**：AI 之间交接，最该传的不是"结论"，而是 **[证据 + 范围 + 硬前提 + 验收方式]** 这四件套。

## 3. 四条升级路径（按性价比排序）

### 路径 1：任务书资产化（0 元，立刻可用）✅ 已落地本套

- 把反复出现的任务书结构固化成模板（§5），把踩过的坑固化成"过期清单"（`15-过期决策清单.md`）。
- 效果：新任务不用从"你帮我看看"开始，直接进"照这个范围改"。
- 代价：一次性整理，之后每次几分钟。

### 路径 2：项目上下文常驻（0 元）✅ 已落地本套

- `13-升级版上下文.md` = 任何模型的开场记忆；`01-决策时间线` = 为什么变成现在这样；`02-过期清单` = 别走回头路。
- 效果：把"解释背景"的轮次从 30 轮压到 3 轮，**这才是省额度的主战场**。
- 维护：每次重大改动后，只更新 §3 状态表和 §8 摘要，不必重写全文。

### 路径 3：对抗式校验（0 元，质量提升最大）

- 同一份 diff，交给**第二个窗口/第二个模型**专门找错，要求它只输出"哪一行会出问题、为什么"。
- 这份对话里已经发生过等效物：DSH 自己发现 `onActivate` 漏导出、发现 `inspectedToday` 不是 Set —— 都是"执行者反过来挑错"。
- 建议固定动作：**DB 迁移、RLS、并发、状态机**四类改动必须过一遍对抗校验。

### 路径 4：付费兜底（要花钱，按次）

- 只在两种情况用：**① 当天网页端被限额卡死且任务紧急；② 高风险决策**（数据库结构、并发、数据迁移）。
- 成本量级（**估算，未实测**）：一次策略会话按累计输入 60k / 输出 8k token 计，Pro 约 **0.4–0.8 元**（空闲/峰时），Flash 约 **0.1 元**。
- 结论：这不是订阅级成本，是"几毛钱一次"。**不要为省钱把策略降级到 Flash**——归档里已证明，同一个烂方案在 Flash 上会反复返工，返工成本远高于几毛钱。

### 不建议的路

- 把整段长对话丢给执行模型"你自己看着办"——它会过度发挥（曾把加时间徽标改成重写渲染函数，直接白屏）。
- 没有验收标准的批量重构。
- 为了"更先进"而引入构建工具——这个项目最大的资产就是零构建。

## 4. 什么时候该花钱，一张表

| 场景 | 用网页端 | 用 API Pro | 用 Flash/DSH |
|---|---|---|---|
| 现场报错、要快速定位 | ✅ 首选 | 限额时兜底 | 可以读代码但不能拍板 |
| 写任务书 / 审 diff | ✅ 首选 | 高风险改动时双跑 | ❌ 不拍板 |
| DB 迁移、RLS、并发设计 | ✅ + 对抗校验 | ✅ 值得花钱 | 只做执行 |
| 大批量机械改动（改名、清理） | 出规范 | 不必 | ✅ 执行 |
| 探索新方向（如国内迁移） | ✅ | 可以 | ❌ 容易给半成品方案 |

## 5. 任务书模板（复制即用）

```text
【仓库/分支】<路径>，分支 <branch>（不要切分支，不要 push）
【目标】<一句话>
【已确认的根因】<证据：哪个文件哪一行 / 哪条 SQL 输出 / 哪个 Response 字段>
【只做这些改动，按优先级】
  1. <文件:行号> <做什么>（为什么：<证据>）
  2. ...
【明确不做】
  - 不改 <文件>；不引入依赖；不重排编码；不动 DB
【硬前提】
  - <例如：规则必须作用在 L146 之前，注入 L148 无效（已实测）>
【验证要求】
  - node --check；离线样本 <S01> 期望值对比；三页面渲染冒烟
【输出】
  - unified diff（不要 commit、不要 push）
  - 自测结果表（期望 vs 实际）
  - 主动列出未闭环项
```

## 6. 回执模板（DSH → 策略模型）

```text
1) git status --short 原文
2) unified diff 全文
3) 自测：命令 + 原始输出（贴原文，不要总结）
4) 未闭环项 / 我做的与指令不一致的地方（必须主动写）
```

## 7. 上线前 5 分钟验收清单

1. 强刷（`Ctrl+Shift+R`），Console 无报错。
2. 首页：清单、汇总行、交期临近正常。
3. 订单列表：卡片/进度/筛选正常。
4. 订单详情：推进/暂停/恢复可用；**测一次双 active 守卫**（暂停当前 → 激活下一道 → 回去点恢复，应被拦）。
5. 新建订单：备注提示可见；第二步能选到新工序（如「喷金油」）。
6. 断网刷新：应显示「网络连接异常」，不是登录页。

## 8. 这套东西如何跨模型复用

- **给任何新 AI 的最小包**：`13-升级版上下文.md` + `15-过期决策清单.md`。前者让它知道现状，后者让它别走回头路。
- **给"要写代码"的 AI**：再加 本文 §5 任务书模板 + 仓库本身（代码是唯一事实源）。
- **给"要做决策"的 AI**：再加 `14-决策时间线.md`，让它知道每个选择当时的约束。
- 三份文件都不含密钥、不含账号，可以直接放进仓库 `AI_CONTEXT/` 长期维护。

## 代码审阅门禁（review 插件）

- 纯 .md / 文案 / 注释改动：不跑审阅，直接给 diff。
- 少量 .js（< 50 行）：quick。
- 一般功能改动：standard。
- 鉴权 / 数据库迁移 / 并发 / 节点状态机：deep（插件强制，不可降档）。
- 跑之前先用 review_diff 看它打算审什么范围；范围不对就停，不要直接 review_run。
- 报告只认"带文件行号 + 触发条件 + 验证依据"的条目；观点性建议不进报告。
- 审阅只是 AI 层，不替代 CI、不替代人工验收（Ctrl+F5 与 SQL 核对仍要做）。
