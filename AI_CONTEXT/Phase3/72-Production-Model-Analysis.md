## 1. 当前 production_records 模型评估

### 1.1 模型结构

```
production_records
├── order_id        FK → orders      订单关联
├── process_name    TEXT             工序名称（游离于 processes 表之外）
├── status          TEXT             待生产 / 生产中 / 已完成
├── created_at      TIMESTAMPTZ      开始时间
├── completed_at    TIMESTAMPTZ      完成时间
├── duration_minutes INTEGER         自动计算耗时
├── good_qty        INTEGER          良品数
├── bad_qty         INTEGER          次品数
├── operator        TEXT             操作人
└── remark          TEXT             备注
```

### 1.2 设计意图 vs 实际效果

| 维度 | 设计意图 | 实际效果 | 判定 |
|------|---------|---------|:----:|
| 与 order_nodes 关系 | 独立并存，各管各的 | 产生两套状态体系，工人困惑 | ⚠️ |
| 工序绑定 | 通过 process_name 匹配 | 游离于 processes 字典，改名即断裂 | 🔴 |
| 时间记录 | 自动记录开始/完成 | 确实自动化了，不需要工人输入 | ✅ |
| 老订单兼容 | syncForOrder 自动创建占位 | 已删除（会污染数据） | ✅ 已修正 |
| 按钮交互 | 开始生产 / 生产完成 | 与节点"完成"按钮重复，已修复 | ✅ 已修正 |

### 1.3 核心问题：process_name 游离于字典

```
当前：
  production_records.process_name = '电镀'  ← 纯文本
  processes.name                  = '电镀'  ← 字典
  二者之间没有 FK 约束，没有 ID 关联

后果：
  - 工序改名 → production_records 中旧名称变成孤立数据
  - 无法 JOIN processes 获取 type/dept_id 等元数据
  - 统计时必须用字符串匹配，脆弱且慢
```

### 1.4 核心问题：非固定工艺路线工厂的适配性

广州表盘工厂的真实生产特征（来自 Phase 3 工厂调研）：

```
1. 没有"标准路线"
   - 同一客户、同一产品类型、不同图纸 → 不同工序组合
   - 工艺路线由主管根据图纸逐单决定，不是从模板选

2. 工序顺序不完全固定
   - 制二内部：磨板→喷砂→刷纹→电镀 是典型顺序
   - 但具体走哪些、跳过哪些，每单不同

3. 返工路径复杂
   - L1 单节点返工（P16 电镀颜色偏 → 重做 P16）
   - L2 部门段返工（P16 全失败 → 从 P12 磨板重新开始）
   - L3 全流程返工（整批报废 → 从 P01 开始）

4. 生产不是线性流水线
   - 电镀是批量挂架，不是单件流
   - 多订单在制二排队等电镀槽
   - 喷漆和电镀可能互斥（选一种）
```

**production_records 的"待生产→生产中→已完成"三态模型假设了一条线性路径。对于非固定路线工厂，这个假设过于简化。**

### 1.5 适用性判定

| 场景 | production_records 适配度 |
|------|:------------------------:|
| 工序顺序固定、每单必走全部工序 | ✅ 高 |
| 工序可选、主管逐单决定路线 | ⚠️ 中（需要为每单创建对应记录） |
| 返工频繁、路径不可预测 | 🔴 低（无法表达"这是返工的第2次P16"） |
| 批量生产、多订单共享工序队列 | 🔴 低（无排队/批次概念） |

**结论：production_records 适合作为"生产时间日志"而非"生产流程引擎"。它记录已经发生的事情，但不适合驱动未发生的事情。**

## 2. order_process_history 履历模型分析

### 2.1 概念定义

```
order_process_history = 订单工序履历表

不是"当前状态快照"，而是"完整事件时间线"。

每个事件记录：
  - 什么时间（when）
  - 哪个订单（which order）
  - 哪道工序（which process）
  - 发生了什么变化（what changed）
  - 谁操作的（who did it）
  - 上下文（context）
```

### 2.2 与 production_records 的核心差异

| 维度 | production_records | order_process_history |
|------|-------------------|----------------------|
| 数据粒度 | 每订单每工序一行 | 每事件一行 |
| 状态模型 | 三态（待生产/生产中/已完成） | 事件流（进入/开始/暂停/恢复/完成/返工/异常） |
| 时间表达 | created_at + completed_at | 每事件带时间戳 |
| 返工表达 | 无法区分（同工序只有一行） | 天然支持（每次返工 = 新事件组） |
| 暂停/排队 | 不支持 | 天然支持（暂停事件 + 恢复事件） |
| 操作追溯 | operator 字段 | 每事件记录操作人 |
| 与 order_nodes 关系 | 弱关联（process_name 匹配） | 强关联（FK → order_nodes） |

### 2.3 建议模型设计

```sql
CREATE TABLE order_process_history (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id        UUID NOT NULL REFERENCES orders(id) ON DELETE RESTRICT,
    node_id         UUID REFERENCES order_nodes(id) ON DELETE SET NULL,
    process_id      UUID REFERENCES processes(id) ON DELETE SET NULL,
    process_name    TEXT NOT NULL,              -- 冗余快照，防止改名断裂
    event_type      TEXT NOT NULL,              -- 事件类型
    status_before   TEXT,                       -- 变更前状态
    status_after    TEXT,                       -- 变更后状态
    good_qty        INTEGER,
    bad_qty         INTEGER,
    operator        TEXT,
    dept_id         UUID REFERENCES departments(id),
    note            TEXT,
    created_at      TIMESTAMPTZ DEFAULT now()   -- 事件发生时间
);

-- 事件类型枚举（CHECK 约束）
-- event_type IN (
--   'node_entered',      -- 订单进入工序
--   'production_started',-- 开始生产
--   'production_paused', -- 暂停（缺料/待确认/人员调配）
--   'production_resumed',-- 恢复
--   'production_done',   -- 生产完成
--   'qc_passed',         -- QC 通过
--   'qc_rejected',       -- QC 拒收
--   'rework_triggered',  -- 触发返工
--   'exception_recorded',-- 记录异常
--   'order_completed'    -- 订单完成
-- )

CREATE INDEX idx_oph_order    ON order_process_history(order_id, created_at);
CREATE INDEX idx_oph_node     ON order_process_history(node_id);
CREATE INDEX idx_oph_process  ON order_process_history(process_id, created_at);
CREATE INDEX idx_oph_type     ON order_process_history(event_type, created_at);
```

### 2.5 相对于 production_records 的优势

| 优势 | 说明 |
|------|------|
| **返工可见** | 每次返工都是一组新事件，不会被覆盖 |
| **暂停可追踪** | 暂停→恢复的时长自动可算 |
| **QC 节点明确** | QC 通过/拒收是独立事件，不是生产记录 |
| **多操作人** | 不同事件可由不同人记录 |
| **完整审计** | 任何时间点的状态都可以还原 |
| **统计灵活** | 可统计"制二平均电镀耗时""返工率""QC拒收率" |

### 2.6 实现代价

| 代价 | 说明 |
|------|------|
| **数据量** | 每订单约 20-50 行（vs production_records 的 10-15 行） |
| **迁移** | 需要从 production_records + order_nodes 联合生成初始履历 |
| **UI 改动** | 订单详情页的"生产轨迹"需要重构为事件时间线 |
| **与现有节点系统关系** | 需要明确：history 是节点的补充日志，还是替代 production_records |

### 2.7 建议：并存过渡

```
Phase 4（当前→近期）:
  production_records 继续作为当前生产状态记录
  order_process_history 作为新增的审计日志表
  两表共存，通过 order_id + process_name 关联

Phase 5（中期）:
  新增事件通过 order_process_history 记录
  production_records 降级为"当前状态缓存"（从 history 聚合计算）
  逐步减少对 production_records 的直接写入

Phase 6（远期）:
  production_records 可废弃
  order_process_history 成为唯一数据源
  所有统计/展示从 history 计算
```

### 3.2 工序分类体系

基于 `processes.type` 字段的三类工序，与 production_records 行为差异：

```
┌──────────────────────────────────────────────────────────────┐
│ 加工工序 (type='加工', 22道)                                  │
│ 改变产品物理状态：冲/磨/喷/镀/印/装                            │
│ 需要记录：开始/完成时间、良品/次品数                            │
│ 工人操作：开始生产 → 生产完成                                   │
├──────────────────────────────────────────────────────────────┤
│ 检验工序 (type='检验', 5道: P23/P24/P25/P35 + 部门内QC)        │
│ 判断产品质量是否可流入下一工序                                  │
│ 需要记录：通过/拒收、缺陷类型、数量                             │
│ 工人操作：QC通过 / QC拒收（触发返工）                           │
│ ★ 这是质量门禁，不是普通工序                                    │
│ ★ 制一虽无独立QC编码，但实际有部门内QC                          │
├──────────────────────────────────────────────────────────────┤
│ 辅助工序 (type='辅助', 8道)                                    │
│ 支持性工作：清洗/撕胶/平压/移交                                 │
│ 通常不需要数量记录                                              │
│ 工人操作：确认完成（单按钮）                                     │
└──────────────────────────────────────────────────────────────┘
```

### 3.3 关键节点（Bottleneck & Control Points）

| 节点 | 类型 | 为什么关键 | 建议采集 |
|------|:----:|-----------|---------|
| **P16 电镀** | 加工·必经 | 全厂瓶颈，挂架批量，多订单排队等槽位 | 等待时长、槽位、颜色参数 |
| **P13 喷砂** | 加工 | 影响后续电镀附着力 | 砂型（重/轻/中） |
| **P15 太阳纹** | 加工 | 影响表盘最终外观 | 纹理方向/密度 |
| **P23 QC板面** | 检验·必经 | 制二中间检验，决定是否进入瓶颈工序P16 | 缺陷类型、拒收率 |
| **P24 QC排版移交** | 检验·必经 | 部门间移交，责任划分关键 | 移交数量、交方/收方 |
| **P25 QC接板移交** | 检验·必经 | 接收方确认，防止数量争议 | 接收数量、差异记录 |
| **P35 总QC** | 检验·必经 | 最终质量门禁，决定是否出货 | 缺陷类型、处理方式、通过率 |

### 3.4 QC 节点设计

QC 节点与加工节点的核心差异（基于 `processes.type='检验'` 区分）：

```
加工节点流程（22道）：
  [开始生产] → 生产中 → [生产完成] → 记录良品/次品

QC 节点流程（5道: P23/P24/P25/部门QC/P35）：
  [开始检验] → 检验中 → [通过] → 进入下一工序
                      → [拒收] → 触发返工 / 特采 / 报废

QC 节点独有数据：
  - 抽检数量
  - 缺陷类型（色差/电镀不良/划伤/沙眼/变形...）
  - 缺陷数量
  - 判定结果（通过/拒收/让步接收）
  - 处理方式（返回上工序/重做/特采/报废）
```

| 节点 | 采集信息 | 采集时机 | 采集方式 |
|------|---------|---------|---------|
| P13 喷砂 | 砂型（重/轻/中） | 开始生产时 | 下拉选择 |
| P14/P15 纹理 | 纹理方向/类型 | 开始生产时 | 下拉选择 |

### 3.6 必经工序（is_required）vs 实际工艺路线

工厂认定的 11 道必经工序并不意味着每单都走它们——`is_required` 代表"如果选了这条路线，这些工序不可跳过"：

```
必经工序分布：
  制一: P01 冲板, P03 焊脚, P06 撕胶纸        (3道)
  制二: P16 电镀, P17 打底, P19 消光,          (7道 — 密集)
        P20 烤板, P23/P24/P25 QC
  制三: —                                      (0道 — 印刷全可选)
  制四: —                                      (0道 — 装配全可选)
  总QC: P35 总QC                               (1道)

这说明：
  1. 制二是质量控制最严的部门，也是唯一有编码QC节点的生产部门
  2. 制三/制四的工序全部可选——取决于客户要求
  3. 总QC是唯一不可绕过的最终节点
```

## 4. 扫码枪方案分析

### 4.1 方案概述

扫码枪 = 条形码/二维码扫描器 + 系统操作触发

三种操作模式对应三种角色：

| 模式 | 角色 | 触发 | 操作内容 |
|------|------|------|---------|
| A: 工人操作 | 普通工人 | 扫订单号 → 系统自动开始/完成 | 单按钮 |
| B: QC操作 | QC检验员 | 扫订单号 → 进入QC判定界面 | 判定+输入 |
| C: 部门节点 | 部门组长 | 扫订单号+工序码 → 部门级操作 | 查看队列/手动干预 |

### 4.2 方案A：普通工人操作

**场景：** 工人拿到一批表盘，扫码后系统自动记录"开始生产"，做完后再次扫码记录"生产完成"。

**物理流程：**

```
工人拿到批次
    │
    ▼
扫订单二维码 → 系统查找当前订单的 active 节点
    │            ├─ 找到 → 自动"开始生产"
    │            └─ 已经是生产中 → 自动"生产完成"
    ▼
进行生产
    │
    ▼
（可选）再次扫码 → "生产完成" + 输入良品/次品数
```

**技术实现：**

```
1. 订单卡片打印二维码
   内容：DF://{order_id}
   贴在批次流转箱上

2. 扫码枪设置为键盘输入模式（HID）
   扫码 = 输入一串文本 + 回车

3. 系统监听全局键盘输入
   - 匹配模式：DF://xxxxxxxx-xxxx-xxxx
   - 防抖：200ms 内连续输入视为一次扫码
   - 触发：自动调用 onStartProduction 或 onCompleteProduction

4. 反馈：
   - 成功：绿色闪烁 + 提示音
   - 失败：红色闪烁 + 错误提示
```

**成本分析：**

| 项目 | 成本 |
|------|------|
| 扫码枪硬件 | ¥50-200/台（USB有线） |
| 二维码打印 | ¥0（订单详情页可直接显示，A4打印） |
| 系统开发 | 1-2天（HID监听 + 自动操作逻辑） |
| 培训成本 | 极低（"扫一下开始，再扫一下完成"） |
| 可靠性 | ⚠️ 如果工人忘记扫码/扫错单，数据会错 |

**可行性：高。** 适合固定工序、单件流场景。不适合批量挂架（电镀一次挂50件，不能每件都扫）。

### 4.3 方案B：QC操作

**场景：** QC检验员扫码后进入该订单的QC判定界面，记录检验结果。

**物理流程：**

```
QC拿到批次
    │
    ▼
扫订单二维码 → 打开QC判定界面
    │            ├─ 显示：订单信息 + 当前工序 + 历史QC记录
    │            └─ 自动定位到该订单的QC节点（P23/P24/P25/P35）
    ▼
QC进行检验
    │
    ▼
在界面上操作：
    [通过]         → 自动推进到下一工序
    [拒收-返工]    → 选择缺陷类型 → 触发返工
    [拒收-特采]    → 记录特采原因 → 推进
    [拒收-报废]    → 输入报废数量 → 记录异常
```

**技术实现：**

```
1. 扫码 = 打开订单详情 + 自动滚动到 QC 节点位置

2. QC 界面增强：
   - 快速判定按钮组（通过/返工/特采/报废）
   - 缺陷类型快捷选择（色差/电镀不良/划伤/沙眼/变形...）
   - 数量输入（抽检数/缺陷数）
   - 拍照上传（可选，需要摄像头）

3. QC 统计看板（Dashboard-QC视角）：
   - 今日检验数
   - 通过率
   - 缺陷类型分布
   - 返工率趋势
```

**成本分析：**

| 项目 | 成本 |
|------|------|
| 扫码枪硬件 | ¥50-200/台 |
| 系统开发 | 3-5天（QC界面增强 + 判定逻辑 + 统计面板） |
| 培训成本 | 低（QC本来就要记录检验结果） |
| 数据价值 | 高（首次获得结构化的 QC 数据） |

**可行性：高。** QC 是最适合扫码的场景——QC 本来就要对每批做判定，扫码只是加速了"找到这个订单"的过程。

### 4.4 方案C：部门节点操作

**场景：** 部门组长扫码查看本部门待处理队列，进行批量操作。

**物理流程：**

```
部门组长早上到岗
    │
    ▼
扫部门二维码 → 打开本部门 Dashboard
    │            ├─ 待处理队列（active 节点）
    │            ├─ 进行中（生产中节点）
    │            └─ 今日完成
    ▼
点击订单进入操作
    │
    ▼
（或在物理看板上贴二维码，每个订单一个码）
扫订单码 → 快速完成 / 标记异常
```

**技术实现：**

```
1. 部门 Dashboard 二维码
   内容：DF://dept/{dept_id}
   扫码 → 打开 Dashboard（部门筛选）

2. 部门级操作：
   - 批量激活：选择多个 waiting 节点 → 一键激活
   - 部门移交：完成本部门所有节点 → 自动激活下一部门首节点
   - 异常标记：选中节点 → 快速标记缺料/待确认/插单

3. 物理看板：
   - 每个部门配一个平板/屏幕
   - 显示本部门 Dashboard
   - 扫码枪连接平板
```

**成本分析：**

| 项目 | 成本 |
|------|------|
| 平板/屏幕 | ¥500-2000/台（5个部门 = 5台） |
| 扫码枪 | ¥50-200/台 × 5 |
| 二维码制作 | ¥0（系统自动生成） |
| 系统开发 | 5-8天（部门Dashboard + 批量操作 + 物理看板UI） |
| 网络 | 工厂WiFi覆盖（已有或需部署） |

**可行性：中。** 需要硬件投入（平板+网络），且需要部门组长改变工作习惯。建议在方案A/B验证后再推进。

### 4.5 综合评估

| 维度 | 方案A 工人操作 | 方案B QC操作 | 方案C 部门节点 |
|------|:---:|:---:|:---:|
| 硬件成本 | 低 | 低 | 中 |
| 开发成本 | 低 | 中 | 高 |
| 培训难度 | 极低 | 低 | 中 |
| 数据价值 | 中 | 高 | 中 |
| 适合扫码 | ⚠️ 批量场景不适合 | ✅ 天然适合 | ⚠️ 组长更习惯看屏幕 |
| 推荐优先级 | **第2优先** | **第1优先** | 第3优先 |

**推荐实施顺序：**

```
Phase 4-A：方案B（QC扫码）
  - 投资回报最高
  - QC数据从"无"到"有"
  - 开发量可控

Phase 4-B：方案A（工人扫码）
  - 在非批量工序试点（装钉/网印）
  - 评估扫码率（工人是否会忘记扫码）

Phase 5：方案C（部门看板）
  - 需要硬件投入和流程变革
  - 在A/B验证后再决定
```
